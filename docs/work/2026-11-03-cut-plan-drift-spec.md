# Cut impact checks no longer drift every apply

Status: active

Date: 2026-11-03. Owner: tier engine and drift check (`cli/tier_ahead.go`, `cli/tier_scan.go`, `cli/tier_engine.go`, `cli/tier_listeners.go`, `cli/plan_drift.go`, `cli/plan_replay.go`, `cli/relay_session.go`, `cli/plan_store.go`; recompute call sites `cli/verb_apply.go`, `cli/confirm_window.go`, `cli/verb_apply_batch.go`). Target: 0.28.1 (App 0.13.14). Changes typed-verbs spec I3 (`docs/work/2026-10-14-typed-verbs-spec.md`).

## Report (Markus, CLI 0.28.0, Relay 0.13.13, local and cloud)

An update of an automation whose helper about 11 automations react to (`input_boolean.presence`) could not be saved. Every `plan write` took about 30 s, said `LIMIT_CUT: read budget`, and listed other consumers each run (1, 4, 5), with `BLUEPRINT_UNRESOLVED` in some runs only. Every `apply` answered `PLAN_DRIFT`, also after the phone had asked.

## Root cause

1. **The clock decided where the check stopped.** The walk itself is deterministic (sorted, and prefetches only warm the session memo), and its count limits (64 acted entities, 200 nodes, 100 consumer configs, depth 8) are too. But it is depth first: each acted entity cost about four reads in a row (relations, consumer states, consumer configs, the next step's states), plus one per blueprint substitution, also in the listener scan. A fake with 11 consumers two levels deep needed 107 reads in about 87 sequential round trips; at a cloud round trip that is the 30 s session budget. Where the budget ran out depended on latency, so each run read another set of configs and listed other consumers. The cut alone also made the plan typed (the full check of that fake is a preview).
2. **Drift needed the identical basis.** `sameAsConfirmed` (I3's exception) required every config the walk read to be the same set. Two cut runs almost never read the same set.
3. **Timing made reasons that name an entity.** A blueprint substitution that ran out of budget became `BLUEPRINT_UNRESOLVED` of that automation, and `sayKey` counted only the listener scan's gaps and an entity-less `LIMIT_CUT` as the one gap sentence the preview says for every gap.
4. The window and the phone already check again before they ask (`humanPlan`). The phone asked because that check happened to stop where the plan had; the check before the save, a new 30 s walk, stopped elsewhere.

## Decision

- **Breadth-first read-ahead** (`readAhead`). Before an entity's consumer scan, its consumer closure is read level by level in parallel: each level's states and relations, its consumers' states and configs (blueprints substituted in the same pass), then the entities matching consumers name in their actions. It writes only the session memo; the walk still decides everything in its own order from the same answers, so the plan is the one the slow walk would make. It stays inside the walk's own limits (depth, acted entities, consumer configs). The listener scan substitutes its blueprints in parallel too. On the fake: 87 → about 25 sequential round trips, the same 107 reads, the same plan.
- **A failed read is a failed read.** A blueprint substitution with no answer (the budget, a timeout, the Relay's link) is `LIMIT_CUT` or `SCAN_FAILED`; an answer Home Assistant can't substitute, or one that can't be decoded, stays `BLUEPRINT_UNRESOLVED`.
- **A cut plan is replayed** (`cli/plan_replay.go`). A plan whose check was cut keeps the reads its preview made (`reads` in the plan file, not in the hash, sealed with the plan's `channel_seal`): every request, and whether Home Assistant answered it (with data, or with its own refusal of the command), plus the walk's choices that hung on the clock (whether a config the listener scan had loaded still counted; the first choice stands). At apply, and in the window's and phone's check before the ask, the plan is first recomputed as before (`recheck`); a reason the preview didn't say is drift. Otherwise the plan is replayed, even when the recompute has the preview's hash (it may have missed a read the preview had): the answered reads are read again, in parallel, on a budget of their own (15 s); the others fail as they did; read-ahead is off. Any read the preview never made means the home changed where it looked, and an answered read that gets no answer now may have changed: both are drift, whatever the hash, and the plan is computed once more as it is now, its new preview. A replay that matched keeps the reads, so a plan saved from it (the window's chat or form fallback) replays too.
- **What a replay may differ in** (`sameAsConfirmed`). A preview that was cut short and said so, a plan file whose fields make its hash, a replay that asked for nothing new, the same kind, server, action, and tier, the same reasons (`LIMIT_CUT` and `SCAN_FAILED` count as one: a read that had no answer says the same sentence wherever the budget ran out; every other reason with its detail), and the same basis, exactly. A plan file without its reads (made before 0.28.1) is never replayed: only its exact hash passes. One whose seal doesn't cover them is drift.
- **Batches** (`excusedByBatch`, batch spec §4 step 5). After a sibling's verified write, a cut member's replay with that sibling's stored digest back must pass `sameAsConfirmed`; an uncut one needs the exact hash.
- **Call plans read the consumer-manager check up front.** Its two reads (config entries, entity registry) are warmed with the targets' relations, so how far a cut walk got doesn't decide whether a manager reason appears.
- **No adjustable budget.** A bigger budget doesn't make a cut land at the same point, and it pushes plan and apply past the 60 s MCP and 120 s command limits. The read-ahead makes most checks finish; the replay handles the rest.

## Why none of this hides a change

- The replay reads what the preview read, as it is now, and compares the result exactly: a changed config, before value, acted entity, or consumer list is drift.
- A changed answer that sends the walk somewhere new (a new consumer of an entity the preview scanned, a new member of a group or area it expanded, a new automation in the listener table) asks for a read the preview never made: drift, even before the walk can tell what that read would show.
- A read the preview had answered that the replay can't read again (the budget, a timeout, the link) may have changed: drift (`TestApplyRefusesACutPlanThatCouldNotReadAgain`, `TestAReplayThatLostAReadIsDrift`). Only Home Assistant's own answer counts as answered; a Relay transport error never does.
- What the preview could not read is not read in the replay either: the preview said that the check couldn't see everything there, and the user confirmed that. The recompute before the replay still reads on: a reason it finds there (a consumer that unlocks a door, plays media, or reaches a device with a lock) is drift, and no replay overrules it.
- The tier must be equal, so a plan confirmed by code stays on the code path.
- The plan file is untrusted. Its reads are in the plan's seal (an HMAC with the Relay credential, as the channel and prompt are): an edited list makes apply refuse the plan, and a batch member whose embedded list was edited (a batch binds its members by hash only) is not replayed, so its cut check is drift. The replay reads through the same read-only allowlist as every plan read.
- The read-ahead never sets engine state (states, configs, basis): it reads through the session only, so the walk's answers are the same ones it would have asked for itself (the tier golden tests pass unchanged). The check right before the save stays.

## Known limits

- A replay that can't read again what the preview read (Home Assistant still too slow) is drift.
- A cut plan's check can take up to 45 s (the 30 s recompute, then the 15 s replay), before the ask and again before the send.
- A preview that was cut (typed) whose recompute completes is a new preview plan (tiers differ). It needs no code, and nothing was sent.
- Beyond where the preview got, a recompute that read a consumer config but could not read what it acts on (the budget) shows a gap, not that consumer's reason: the preview's gap covered it too.
- The read-ahead follows literal `entity_id` targets. Area and device selectors and stored script, scene, and automation runs stay serial; the replay covers their cuts.
- The listener scan's `CALL_SERVICE_LISTENER_UNEXPLAINED` and `RUN_EVENT_LISTENER_UNEXPLAINED` appear only when its table completes, so a recompute that gets further than a cut preview can add one: drift (fail closed).
- A cut plan made before the update (no reads in its file) drifts once and is planned again.
- The listener scan's own config reads stay gaps in a replay, as in any recompute on `main` (`TestApplyKeepsACutPlanWhoseGapsDiffer`): they never enter the basis, so one the preview read and the replay can't is one more "check cut short", not drift.
- A cover state that times out on a lock's device still reads as an access sibling (fail closed; `TestDeviceAccessSiblingOnEveryPath`), which a cut check may reach in one run only.
- The MCP form (`confirmByForm`) still asks from the stored plan before apply checks it; a drift there wastes the form's answer. The CLI's window and phone, and the chat bridge's phone, check first.
