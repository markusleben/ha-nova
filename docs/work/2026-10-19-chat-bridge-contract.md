# Chat-app bridge contract: `ha-nova serve` (2026-10-19)

Status: active

Parent spec: `docs/work/2026-10-18-onboarding-0.27-spec.md` §11. Scope: the contract between `ha-nova serve` (the bridge, PR train B1), the NOVA App that runs it and writes its files (B2), and the Home Assistant integration that forwards to it (B3). Behaviour beyond this contract is the code in `cli/mcp_serve.go` and `cli/mcp_serve_phone.go`.

## Path

Chat app → Home Assistant OAuth → integration view `/api/ha_nova/mcp` (pure pass-through) → `ha-nova serve` on an internal port of the App container → Relay → Home Assistant.

## Command

`ha-nova serve --listen <host:port> --data-dir <dir> --secret-file <file> [--confirm-wait 25s] [--rate-limit <n>] [--server <name>] [--control-listen <127.0.0.1:port> --control-secret-file <file>]`

- `--listen`: an explicit host is required (the App passes `0.0.0.0:<port>`, never mapped to the host).
- `--secret-file`: exactly 64 lowercase hex characters (256 bits), mode `0600`. Read once at start.
- `--control-listen` with `--control-secret-file` (0.28) serve the NOVA App's control channel (below) on a listener of its own. It binds a loopback IP only (`127.0.0.1` or `::1`). The secret file follows `--secret-file`'s rules and must differ from it. Give both or neither; without them no control endpoint exists (the hosted demo).
- `--confirm-wait`: 1 s to 2 min; how long one `ha_apply` waits for a phone tap.
- `--rate-limit`: at most n requests per minute per Home Assistant user (fixed window), then `429` with a JSON-RPC error (code `-32001`, "Wait a minute"); `0` or absent: no limit (the App sets none). Used by the hosted demo (`docs/work/2026-10-20-demo-add-to-claude-spec.md`).

## HTTP

- `POST /mcp`, one JSON-RPC message per request, one JSON answer (`application/json`). Notifications and responses get `202` with no body. `GET` and `DELETE` get `405`. No SSE, no sessions (`Mcp-Session-Id` is accepted and ignored; none is issued), no elicitation.
- `Mcp-Protocol-Version`: a legacy revision (`2025-11-25`, `2025-06-18`, `2024-11-05`) selects that era; absent means `2025-11-25`; `2026-07-28` requests carry `_meta` per request; any other value gets `400`.
- Body limit 1 MiB.

## Authentication (every request)

1. Exactly one `Authorization: Bearer <secret>`, compared in constant time.
2. Exactly one `X-HA-User-Id`: the Home Assistant user the integration authenticated (`^[0-9a-f]{32}$`).
3. That user is allowed (below).

Refusals: 1–2 → `401`, 3 → `403`, unreadable settings or a failed read of Home Assistant's users → `503` (a listed user must also be an active, not system-generated user there, else `403`). The integration must set both headers itself, from its own secret and `request["hass_user"]`, and must drop any client-sent copies. The user header is trusted only together with the secret.

## Files in `--data-dir` (written by the App)

- `chat-apps.json`, re-read on every request. Unknown fields or trailing data refuse every request.
  - `allowed_users`: list of HA user ids. Absent means the HA owner only; an empty list allows nobody.
  - `read_only` (default `false`): refuses `ha_call`, `ha_plan`, and `ha_apply`.
  - `chat_codes` (default `true`): with `false`, a typed plan needs the user's linked phone.
  - `levels` (0.28): `{"<HA user id>": "ask" | "use" | "manage"}`, the owner's choice per listed user. A user's level is the lower of that and their Home Assistant role (the owner or `system-admin`: `manage`; `system-users`: `use`; anything else: `ask`); with no choice stored, the role's. An unknown level name refuses every request.
  - `roles` (0.28): `1` whenever the App writes `allowed_users`, so a 0.27 bridge, which refuses unknown fields, refuses the file after a rollback instead of giving every listed user full power. Any other number, or `levels` without `roles: 1`, refuses every request.
  - A listed user who is inactive or system-generated in Home Assistant is refused (`403`).
- `phone-links.json`: `{"<HA user id>": {"service", "device_id", "user_id", "name"}}`, the bridge's only link store (never a computer's `config.json`). A link's `user_id` must equal its key; `null` or a malformed entry is an unusable link (refused, never "no phone"). An unreadable file refuses typed plans. The bridge's control channel (below) writes it; once the App uses that channel, it is the file's only writer.
- Write both files atomically (temporary file plus rename): a missing `chat-apps.json` means the defaults.
- `users/<hash>/`: owned by the bridge (per-user plans).
- `activity.jsonl` and `seen.json` (0.28): owned by the bridge (`0600`), read only through the control channel. One line per change a chat app made or tried (time, user id, the user's name then, tool, service or plan kind, at most 10 target names, and `done`, `phone`, `code`, `declined`, `refused`, `failed`, or `unknown`), never a read, a chat text, a code, or service data; the last 500 lines of the last 30 days, at most 100 of them refusals (a service name that isn't one adds no line). `seen.json` keeps the hour of each user's last request.

## Tools and confirmations

- The same 10 tools, server instructions, and verbs as `ha-nova mcp`. Plans and pending phone asks are bound to the HA user that made them; another user's plan id (in `ha_apply` and in a `waiting_for_phone` re-call) answers exactly like an unknown plan.
- Typed plans: the linked phone of the requesting HA user (at Use the home or more), else, at Manage everything only, a chat code unless `chat_codes` is `false`. Never a window or a form. The code's `say` is only what will happen (the action and its reasons, "Nothing has run yet."), then the line above the code with how long it works ("Type this code within 15 minutes:"), and the code on the last line; the result leads with `answer_rule` ("Show `say` in the user's language, every line translated…; Nothing after the code."), carries no `notices` but a draft's, and the low-protection note ("I can see this code too…") lives in the server instructions, since the bridge has no MCP sessions to say it once per session (claude.ai moved every other note below the code, a separate expiry line too; 0.27.2).
- `ha_apply` on a phone plan waits up to `--confirm-wait` (default 25 s pending the Home Assistant Link timeout test; spec §11.4 names 45 s), then returns `status: waiting_for_phone`. Calling again joins the same ask (no new notification). A tap applies at once; the owner's switches are re-checked before it applies. One open phone ask per user (`CONFIRM_PENDING` otherwise). An ask stays open 3 min or until the plan expires.
- The integration's own timeout must exceed `--confirm-wait` plus about 10 s, and must map its timeout to a readable error.
- **Levels (0.28)** (spec `docs/work/2026-10-24-chat-apps-household-spec.md`, code `cli/mcp_serve_levels.go`): every tool, argument, and plan kind has a decided level; anything not listed is refused at every level. Ask only: `ha_skill`, `ha_find`, `ha_get` (without `config`, `related`, `references`, `dashboard`, or `dashboards`), and `ha_history`. Use the home adds `ha_call` without `skill` (or with exactly `ha-nova:media` on `media_player.*`), inside an allowlist checked on the service and every resolved target (device domains, `scene.turn_on`, running a script, `automation.trigger`, and `homeassistant.turn_on/turn_off/toggle` on devices only), and `ha_apply` of the user's own `call` plans without `no_snapshot`. Everything else needs Manage everything: `ha_map`, `ha_trace`, `ha_read`, `ha_plan`, and applying any other plan kind, `batch` included. A refusal is the tool's envelope with `CHAT_LEVEL` and a plain `next` (a config plan of a user who isn't an administrator: `ADMIN_ONLY` first). Reads use Home Assistant's users as read within the last minute; every change (`ha_call`, `ha_apply`, a phone tap's apply) reads them again, and an unreadable list refuses (`503`, or `ACCESS_UNKNOWN` in the envelope before a change). At apply, the plan's kind and, for a call, its service and targets are checked against the level read then.

## Control channel (0.28)

Spec: `docs/work/2026-10-24-chat-app-phone-move-spec.md`. Code: `cli/mcp_serve_control.go`, `cli/mcp_serve_control_job.go`. Served only on the `--control-listen` listener, never on `/mcp`. JSON in and out; every request carries exactly one `Authorization: Bearer <control secret>`, else `401 UNAUTHORIZED`. An error is `{"error": {"code", "message"}}`; any other path or method answers `404 NOT_FOUND`.

- `GET /control/v1/phones?user=<HA user id>` answers `{"phones": [{device_id, name, platform}], "link": null | {name, device_id, platform, state, why}}`.
  - `phones` are that user's own phones that can confirm: on their person, the user allowed at Use the home or more and not the Relay's user, and a name no other device shares. The linked phone is left out.
  - `platform` is `ios`, `android`, or `""` (unknown). The page needs it because an iPhone shows the buttons on a press and hold.
  - `state` is `ready`, `gone`, or `unavailable`. Only `override` replaces a `gone` phone, and nothing replaces an `unavailable` one. `why` says which:
    - `gone`: `removed` (the phone is no longer in Home Assistant, or the entry is `null` or names another user), `not_allowed` (its user may no longer confirm on a phone: not allowed, below Use the home, or inactive), or `relay_user` (its user is now the Relay's).
    - `unavailable`: `unreachable` (its notify service is gone) or `shared_name`.
  - Errors: `400 INVALID_USER`. `503 PHONES_UNREADABLE` when Home Assistant or `phone-links.json` is unreadable. `409 OWNER_TOKEN` when the App's Relay signs in as the owner: a tap can't be told apart from HA NOVA itself, so no phone is listed or linked, as on a computer.
- `POST /control/v1/phone` takes `{"user", "action", "phone"?: {device_id, service?, name?}, "override"?: false}` and refuses unknown fields (`400 INVALID_REQUEST`).
  - `adopt` stores the user's first link, handed over from a computer link that the user's own tap made. No question is sent. `phone.device_id` must be one of the user's `phones`; the bridge takes the service, name, and platform from Home Assistant, whatever the request says. Answers `200 {"status": "done"}`, or `409 PHONE_EXISTS` when the user has an entry, `null` included.
  - `move` (`phone.device_id` from `phones`) answers `202 {"job", "status": "running"}`. The phone linked now asks first ("Move chat-app confirmations?" [Move]), then the new phone ("Get chat-app confirmations?" [Allow]). The new phone's tap must arrive as `user`. With no link yet, only the new phone asks. Refused before anything is sent: `409 PHONE_NOT_ELIGIBLE`, `PHONE_ALREADY_LINKED`, `OLD_PHONE_UNAVAILABLE`, and `OLD_PHONE_GONE` without `override`.
  - `stop` answers `202` with a job: the phone linked now asks ("Stop chat-app confirmations?" [Stop]), then the entry goes. A `gone` phone with `override` is removed at once (`200 done`). Otherwise `409 NO_PHONE`, `OLD_PHONE_UNAVAILABLE`, or `OLD_PHONE_GONE`.
  - `drop` removes the entry with no question, only for a user who is no longer allowed (`409 USER_STILL_ALLOWED` otherwise), and answers `200 done`.
  - Checked first: `400 INVALID_USER`, `INVALID_ACTION`, and `INVALID_PHONE` (`adopt` and `move` need `phone.device_id`). Every action, `drop` included, holds the user's one change at a time: `409 PHONE_CHANGE_RUNNING`. Every action but `drop` needs an allowed user (`403 USER_NOT_ALLOWED`). `503 SETTINGS_UNREADABLE` when `chat-apps.json` or Home Assistant's users can't be read. `adopt`, `move`, and `stop` also answer `503 PHONES_UNREADABLE` and `409 OWNER_TOKEN` as `phones` does.
  - A change made at once (`adopt`, `drop`, a `stop` with `override`) checks again right before it writes: `409 PHONE_CHANGED` (the entry changed meanwhile), `409 ACCESS_CHANGED` (the user's access changed meanwhile), `503 SETTINGS_UNREADABLE`, or `503 LINKS_UNWRITABLE` (`phone-links.json` can't be read or written).
  - `override` is the NOVA page's click (the owner's browser session and a single-use CSRF token). The App never sends it from its machine API.
- `GET /control/v1/phone/<job>?user=<HA user id>` answers `{"status"}` of a job started for that user (`400 INVALID_JOB` for a malformed id, `400 INVALID_USER` for a missing or malformed user). Another user's job reads as `lost`, as an unknown id does.
  - From the `202` on it adds `step` (`old` or `new`), `phone` (the phone that step asks), and that phone's `platform`: while `running` the step now, at the end the last one, so the page can name the phone that cancelled or didn't answer. A move also has `to` (its new phone).
  - It ends as `done`, `declined`, `timeout`, `rejected` (a tap from someone else), `changed`, or `failed`.
  - `changed`: the link, the phone, or the user's access changed meanwhile; for a stop, also the chat-code setting its question named.
  - `failed`: the notification couldn't be sent or heard, a check after a tap couldn't read Home Assistant or the links, or the write failed.
  - Results stay for 10 minutes. An unknown id, e.g. after a restart, answers `lost`: nothing changed, and the caller says to try again.
- **Checks after a tap:** the bridge reads the link and the settings again after each tap. A move asks its new phone only while the user is still allowed. Nothing is written or removed unless the entry is unchanged and the user's access still allows it.
- **Writes** are atomic and `0600` and run under one lock. Each compares the entry the action read first, and the user's access, right before it writes. So a change made meanwhile is never overwritten, and a dropped link never comes back.
- **Phone texts** come from the confirmation catalog (`chat_phone.*`) in Home Assistant's language.
- **Who confirms:** a chat-app phone belongs to its own user while their level is Use the home or more (`phoneAllowed`, read when the bridge reads the phones); a computer keeps `phoneAdmin`. `adopt` and `move` write only while it still holds.
- `GET /control/v1/activity` answers `{"changes": [{at, user, name, tool, what, targets?, result}]}`, the last 20 lines of `activity.jsonl`, newest first. `GET /control/v1/seen` answers `{"users": {"<HA user id>": "<RFC 3339 hour>"}}`.

## App side (B2)

Code: `nova/src/runtime/chat-apps.ts`, `nova/src/runtime/chat-phone-control.ts`, `nova/src/http/handlers/chat-apps.ts`, `nova/src/http/handlers/nova-page-chat-phone.ts`, `cli/mcp_serve_relay.go`. Built only when the image sets `HA_NOVA_CHAT_APPS=1` (`nova/Dockerfile` `ARG`, default `0`); until then nothing below runs, and no route or page section exists.

- **Files** (`/data/chat-apps/`, written atomically, `0600`): `state.json` (`enabled`, `discovery_uuid`), `secret`, `control-secret`, `relay.json`, `bridge/` (the `--data-dir`), `home/` (the bridge's `HOME`).
- **Secret:** 32 random bytes as 64 hex, made on the first turn-on, kept across App restarts and updates, deleted only by turning off. `control-secret` is the control channel's own, made the same way, and also by a bridge start while chat apps are on without one (an update from 0.12.1). Home Assistant and the discovery message never hold it. Going back to 0.12.1 leaves it on turn-off (that App doesn't know it); it never left the App, and a later App uses it again.
- **Internal device credential:** the App mints an ordinary device record in its own registry (`client_install_id` `nova-app-chat-bridge`: a re-mint replaces the old record, and pairing refuses that id) and writes `relay.json` `{"relay_url": "https://127.0.0.1:8792", "spki_pin", "credential"}`. `ha-nova serve --relay-file` uses only that: the Relay's pinned TLS port over loopback, device mode, no `config.json`, keyring, Cloud route, or pairing code. Reused while it resolves (a new TLS pin is written into the same file); re-minted before each bridge start otherwise (registry reset, revocation). The NOVA page never lists it under Devices, and `GET /auth/device/peers` leaves it to `chat_app_files`.
- **Process:** `ha-nova serve --listen 0.0.0.0:8794 --data-dir … --secret-file … --relay-file … --control-listen 127.0.0.1:8795 --control-secret-file …` with only `PATH`, `HOME`, `TZ`, `HA_NOVA_NO_BROWSER` in its environment (never the Supervisor or HA token). 8794 is not in `config.yaml` `ports:`, so only the Supervisor network reaches it. While on, an exit restarts it after 5 s, backing off to 5 min while it keeps failing; turning off sends SIGTERM, then SIGKILL after 7 s.
- **Discovery:** `POST /discovery` `{"service": "ha_nova", "config": {"host": <App hostname from /addons/self/info>, "port": 8794, "secret": <64 hex>}}`; the returned uuid is kept. Supervisor keeps one message per App and service, so the App re-posts on every start while on (an unchanged message is a no-op). Turning off sends `DELETE /discovery/<uuid>`; a 404 counts as gone.
- **Integration files:** only `/config/custom_components/ha_nova`, copied from the image's `/app/integration/ha_nova` (B3 adds it; without it the feature reports unavailable). `custom_components` must be a real folder, the old `ha_nova` is removed (a symlink is unlinked, never followed), files are created exclusively (`0644`). Written on turn-on only, never refreshed on an App update (B3's decision, below).
- **Owner action** (NOVA page form, or `GET`/`POST /chat-apps/v1/state` over ingress: owner only, machine only, JSON only). `POST` fields, all optional: `enabled`, `allow_restart`, `read_only`, `chat_codes`, `owner_phone`, `owner_phone_move`. On/off runs first, so a refusal changes nothing else. On and off (and the start-up resume) never interleave.
  - The owner's chat-app phone changes only through the bridge's control channel (`nova/src/runtime/chat-phone-control.ts`: loopback, the control secret, 10 s for a read and 30 s for a change, which waits for the bridge's lock while a chat app's call reads or writes Home Assistant; answers up to 64 KB). Its `400`, `403`, `409` and `503` refusals pass through with their code; any other status is `503 CHAT_PHONE_UNAVAILABLE`. A bridge that isn't reached, can't be read, or chat apps off: `503 CHAT_PHONE_UNAVAILABLE`, nothing changed. A change whose answer was lost after it went out (a timeout, a reset, a cut-off answer, a job id it can't read): `504 CHAT_PHONE_UNKNOWN`, it may have happened. `owner_phone` and `owner_phone_move` each go alone (`400` with any other field), so a phone refusal never leaves a switch or a turn-on half done. `owner_phone` (`{service, device_id, name}`) is `adopt` for the owner's own user id: a phone the bridge finds among the owner's phones, only while the owner has no entry (`409 PHONE_EXISTS`). Right after a turn-on, Home Assistant may not list the phone yet, so the App tries it again every 2 s for 15 s while the bridge answers `PHONE_NOT_ELIGIBLE` or `PHONES_UNREADABLE`. `owner_phone: null` answers `409 OWNER_PHONE_STOP_ON_PAGE`: a stop asks the phone linked now, from the NOVA page. `owner_phone_move` (`{device_id}`, not with `owner_phone`) is a `move` and answers `phone_job: {id, status: "running"}`. This API never sends `override`.
  - `GET` answers `phone_change: true` (this App moves the chat-app phone; setup checks it before it offers a move) and, after a move started through this API, `phone_job`: the bridge's state of that job, or `status: "unread"` while the bridge can't be read. The App keeps only the last one, in memory, and leaves it out while chat apps are off.
  - Turning on refuses, before any change: `409 HA_TOO_OLD` (Home Assistant before 2026.10); `409 RESTART_CONSENT_REQUIRED` when Home Assistant does not run `ha_nova` yet and `allow_restart` is not `true`; `409 HA_CONFIG_INVALID` when its configuration check fails. Then secret, files, credential, serve, discovery, and only then `enabled: true`; a failure on a first turn-on undoes every step (it stays off, and [Turn on] is the retry). The answer comes first; `homeassistant.restart` follows a second later (Home Assistant carries the ingress connection). The page's [Turn on chat apps] sits under "Home Assistant restarts once (about a minute)." and is that consent.
  - Turning off: serve stops, a restart not yet sent is cancelled, and every registry record with the reserved install id is revoked before any chat-app file is read; then the discovery message, the secret, and the folder; a failed step leaves `unfinished`, and the same action finishes it. An App version that can't run chat apps still offers [Turn off].

- **Chat-app phone on the NOVA page** (the owner's own; spec `docs/work/2026-10-24-chat-app-phone-move-spec.md`): read from `GET phones` on each page load. A `ready` phone shows "Change phone…" and "Stop phone confirmations"; no phone yet, "Link a phone…". "…" opens `?chat_phone=pick`: one form, one CSRF token, a choice per phone that can confirm (the bridge takes only one of the owner's own). A `gone` phone shows why, "Link a new phone…", and Stop, which takes effect at once (the page says what chat apps do then, and `?chat_phone=stopped` says it's done): only these two forms send `override` (`chat_phone_replace`, `chat_phone_remove`). An `unavailable` phone offers nothing, only how to remove it in Home Assistant (`unread`: reload in a moment). A timeout or failure on the phone linked now adds that way out; `lost` (the App or the bridge restarted) points to the Confirmations line. `504 CHAT_PHONE_UNKNOWN` shows "couldn't tell whether this started". A started job redirects to `?chat_job=<id>`, which reloads every 5 s while it runs, names the phone to check (with how its buttons show) and then how it ended. `409 OWNER_TOKEN` and an unreadable list each show one line. The Confirmations line says that changes that need an OK are refused while the linked phone isn't `ready`.

### Known limits (B2)

- Removing the App, or going back to an App without chat apps, while they are on leaves the discovery message (until Supervisor drops it) and the folder; an App version with the code but without the bridge offers only [Turn off].
- A request already running when chat apps turn off may finish within serve's 5 s shutdown, but its Relay credential is revoked at once.
- The NOVA page names the connector path, not the full Link address, and shows "On" before Home Assistant has restarted (setup's step 3 and the CLI show the full address and wait for the restart, B4).
- A discovery message Supervisor accepted while its answer was lost (timeout) has no stored uuid, so turning off can't delete it; it names a stopped bridge and a deleted secret. A discovery re-post that fails at start-up is retried only at the next App start.
- A device that paired with the install id `nova-app-chat-bridge` before pairing refused it would be treated as the bridge (the CLI never sends that id).

## Setup and CLI (B4)

Code: `cli/chat_apps.go`, `cli/command_chat_apps.go`, the step 3 row in `cli/setup_page_control.go` and `cli/setupweb/chat.js`. User doc: `docs/reference/chat-apps.md`.

- **Owner session:** the ingress session of this run's owner sign-in (memory only, `setupOwnerIngress`), the same one that armed the pairing; cleared when a pairing attempt starts, so only a sign-in pairing in that attempt sets it. The row also needs a pairing in this run (as the phone row). It calls `GET`/`POST /chat-apps/v1/state` (`CloudEndpointChatApps*`), never with a device credential. A six-digit-code pairing has no owner session: no row, no question (the NOVA page or `ha-nova chat-apps on` instead).
- **When the row shows (feature detection, no version floor):** the `GET` answers `available: true` (a dormant App answers 404: nothing shows), Home Assistant is 2026.10 or newer (`/api/config` through this computer's Relay), and the connector has an origin: Link's address while its remote access answers, else Home Assistant's `external_url` when it is public HTTPS (`https://`, a hostname whose last label starts with a letter, so no IP in any form; no local-only suffix such as `.local` or `.ts.net`; port 1–65535; no path, query, or user info; a `*.nabu.casa` address counts only through Link; vectors shared by the Go and TS tests in `tests/fixtures/chat-connector-base.json`). Neither: no switch (`noaddress`): off, the row says it needs Link remote access, links Home Assistant's Link page on the saved local address (`link_page`, `/config/cloud`) and the guide's own-address part (`guide`), and its Check again (`chat_recheck`) reads the row again; already on, a line that says so. The text path prints one plain line. Already on: the row shows the address. The NOVA page picks the same origin from `cloud/status` and `get_config` (`chatConnectorUrl`).
- **Add to Claude:** wherever the address shows (step 3 when on, step 4, the NOVA page, `ha-nova chat-apps on|status`), a link to Claude's documented install URL `https://claude.ai/customize/connectors?modal=add-custom-connector&connectorName=HA%20NOVA&connectorUrl=<percent-encoded address>` (`claudeConnectorLink`, Go and TS). Next to it, "Add for my organization" (`claudeOrgConnectorLink`, Go; `claudeConnectorLink(url, true)`, TS): the same parameters on `https://claude.ai/admin-settings/connectors`, because Team and Enterprise members can't add a custom connector, only an owner can. Both carry the address only, never a token; Claude shows the values and asks before adding. The page renders it only when it starts with `https://claude.ai/`, with "Adds <host>" next to it (any Home Assistant admin can set `external_url`, so the owner sees where the connector points). ChatGPT has no documented prefill link: the copy bar and the steps stay.
- **Consent:** the switch only opens the consent ("… Home Assistant restarts once (about a minute)."); "Turn on and restart Home Assistant" posts the page action `chat` with value `on` (A6 action rules), and only that sends `enabled: true, allow_restart: true`. The text path asks the same in one arrow menu, default "Not now"; without the menu only a typed `yes` consents. `ha-nova chat-apps on` checks Home Assistant and Link, signs the owner in, then asks (the consent names the phone that will confirm, or says a code shows in the chat). Finish is disabled while the page's consent is open.
- **Owner phone:** a phone linked on this computer by the owner's own tap goes to the App as `owner_phone` in its own request after the turn-on (also when step 3 links it after chat apps are on), unless the App has one already (spec §11.4).
- **Moving it:** after "Use another phone" with chat apps on, an App with `phone_change` and this run's owner session gets "Chat apps still ask “<old>”. Move them to “<new>” too?" [Move chat apps too] [Keep] (`chat_move`, `yes` or `no`) in place of `setup.chat.phone_kept`. Yes posts `owner_phone_move`, then reads `GET` every 2 s for 4 min at most; the row names the phone to check at each step, then how it ended (the NOVA page shows a result setup couldn't read). `OLD_PHONE_GONE` and `OLD_PHONE_UNAVAILABLE` point to the NOVA page's "Link a new phone…", `PHONE_ALREADY_LINKED` counts as done, `lost` and any 5xx but `503` as unknown, and an expired owner session says so. A re-run without the owner session points to the NOVA page when the App is 0.12.2 or newer (its version through this computer's Relay). An older App, or a phone here that isn't the owner's own, keeps `setup.chat.phone_kept`. The App with no phone yet gets the new phone as `owner_phone`.
- **Ready:** step 3 waits until the `ha_nova` config entry is `loaded` (`config_entries/get` through the Relay), showing the restart (Home Assistant stops answering, then answers again); with a restart to come, only an entry loaded after Home Assistant was down counts. 5 min at most, then one line (restart Home Assistant yourself) and the address anyway. Ctrl+C while waiting: the page ends setup as on step 3's wait; the terminal says on, not started yet. Step 4's notes repeat the address.
- **Failures:** a lost answer (network, timeout, a 5xx other than `OWNER_CHECK_UNAVAILABLE`) is re-read with `GET`: when the App says on, the wait continues; when they were on before, or the re-read fails, the line says HA NOVA couldn't tell. One plain line per App refusal (`HA_TOO_OLD`, `HA_CONFIG_INVALID`, `CONFIG_*`, other), the switch stays and [Turn on] runs the whole action again; an expired ingress session (Supervisor ends it 15 min after its last use) points to the NOVA page.
- **Off:** the NOVA page, or `ha-nova chat-apps off` (owner sign-in, `enabled: false`). Step 3 offers no off.
- **`ha-nova chat-apps status`:** no sign-in; "on" means the `ha_nova` entry is loaded.
- **Refused user:** the bridge answers a signed-in user who may not use chat apps with `403` and a JSON-RPC error (the request's id when it is a string or number, else `null`; code `-32001`): "Only the Home Assistant owner can use HA NOVA in chat apps. Sign in as the owner." (with an explicit `allowed_users` list: "… Sign in with an account the owner allowed.").

## Integration (B3)

Code: `nova/integration/ha_nova/` (copied into the image at `/app/integration/ha_nova`, then by the App into `/config/custom_components/ha_nova`). Tests: `tests/ha_integration/` (pytest against the pinned Home Assistant), CI job `ha-integration` (`ci-gate` needs it). `scripts/check-docs.sh` [5b] fails it on any logic beyond discovery, the proxy, and the user hand-off.

- **Entry:** only from the `hassio` discovery flow, no user step. Data: `host`, `port`, `secret`, and the App `slug`; a malformed message (host not a hostname, port not 1–65535, secret not 64 hex) creates nothing. Unique ID: the message's uuid, because Home Assistant's discovery removal deletes only the `hassio` entry with that uuid (`components/hassio/discovery.py`). A changed message (same uuid) updates the entry and reloads it. A new message from the same App slug (Home Assistant missed the old one's removal) replaces the entry's uuid and data. A message from another App slug is refused while an entry exists. Deleting only the entry is undone by Home Assistant's re-discovery; the App deletes the message instead (B2).
- **View** `/api/ha_nova/mcp`, `requires_auth = True`: Home Assistant's own check (access token, OAuth through Home Assistant Link). Unauthenticated requests get Home Assistant's `401` with `resource_metadata` and never reach the bridge. A signed path (`authSig`, a shareable link) gets `401`; a user Home Assistant made for itself (Supervisor, content user) gets `403`. Registered once; while no entry is loaded it answers `404`.
- **Forwarded:** `POST`, `GET`, and `DELETE` to `http://<host>:<port>/mcp` (the 0.27 bridge answers `405` with `Allow: POST` for the last two); other methods get Home Assistant's `405`. The query string is never forwarded. The body streams both ways, never read, parsed, or logged.
- **Request headers:** only `Content-Type`, `Accept`, `Last-Event-ID`, and `Mcp-*` pass; everything else, including the client's `Authorization`, `Cookie`, and any `X-HA-User-Id`, is dropped. Then exactly one `Authorization: Bearer <secret>` and one `X-HA-User-Id: <the authenticated Home Assistant user's id>`.
- **Response:** the bridge's status, `Content-Type`, `Allow`, and `Mcp-*` headers; nothing else (no `Set-Cookie`). The integration's own client session keeps no cookies. Exceptions, each with a JSON `{"message"}`: the bridge's `401` (wrong secret) becomes `502` "chat-app connection is out of date" (a `401` would send the chat app back to Home Assistant's sign-in); bridge unreachable (incl. 10 s connect timeout) `502`; no answer for 150 s (`sock_read`, above `--confirm-wait`'s 2 min maximum) `504`. A stream cut after the status was sent aborts the connection, so the client sees a broken transfer, never a short answer that looks complete.
- **Never logged:** the secret and bodies (debug lines name only the error class).
- **Version-stable:** the App writes the integration on turn-on only and never refreshes it on an App update, because new integration code needs a Home Assistant restart. A later change to it needs an App update that re-copies it and asks for that restart (not built in 0.27); the bridge must keep working with this version.

### Known limits (B3)

- **R9 (open):** Home Assistant's protected-resource metadata names only the origin. If the maintainer's claude.ai test (spec §13 B0) shows that claude.ai needs the full path, the fallback (an own `401` with an own metadata document whose `resource` is the full `/api/ha_nova/mcp` URL) means a view with `requires_auth = False` that checks Home Assistant's authentication itself: a separate reviewed PR before the release, not built here.
- A timeout or a refused secret answers with plain HTTP errors, not JSON-RPC errors (the integration never reads the request id).
- Any App whose `config.yaml` lists `discovery: [ha_nova]` can announce the bridge while no entry exists, including after turn-off until Home Assistant's next restart (the code stays loaded); App code is trusted, as for every Supervisor discovery.
- Turning chat apps off while Home Assistant is down loses Supervisor's removal push: the entry stays (and fails to load once the folder is gone) until the owner deletes it, or the next turn-on replaces it.
- A changed message reloads the entry; during that moment the view answers `404` (harmless: the bridge is stateless).
- A tool call that waits behind other bridge work for more than 150 s gets `504` while the bridge may still finish it.
- Discovery against a real Supervisor (HAOS VM) is not yet run. The pytest drives Home Assistant's own `hassio` discovery code (add, re-discover after an entry delete, remove by uuid) with Supervisor mocked; the live test bed check replayed the same calls. The real run is a required release lane (spec §12).
