# 0.33 addendum: a headless computer that a bot drives (MAR-244)

Status: active (spec only; built on the `release/0.33` train after the maintainer's go)

Date: 2026-11-18. Parent: `docs/work/2026-11-18-0.33-spec.md` (MAR-243). Owner: setup and pairing (`cli/setup_*.go`, `cli/cmd_pair.go`, `cli/confirm_phone_*.go`), the gate client (`cli/gate_*.go`), the agent's texts (`cli/confirm_strings.*.json`, the skills), and the App's safety check (`nova/src/http/gate-asks.ts`, `nova/src/security/device-registry*.ts`, `nova/src/http/handlers/nova-page*.ts`). High-risk: it adds a way to confirm typed actions.

## Why

Markus paired a computer with no display and no browser on it, which a bot drives while he is away. A risky action waited for a window nobody could see. No notification reached his iPhone, because no phone was linked to that computer and setup didn't get him to link one. The NOVA page was out of reach while he was out. His decisions (MAR-244, 2026-11-18):

- H1: a phone tap is the preferred way to confirm wherever the person links a phone.
- H2: where they don't want to link one, a **four-digit code in the bot's chat is accepted as a fallback**, although the AI sees it, and that limit is described honestly.
- H3: everything works end to end on a computer with no browser on it.

Doors, locks, garages, gates, and the alarm keep a confirmation in every case. Only who may give it changes.

## What happens today (0.32), step by step

1. **Pairing works without a browser.** Over SSH or without a display, `ha-nova setup` skips the browser page (`cli/setup_flow_page.go:39–53`) and the Home Assistant sign-in (`haSignInPossible`, `cli/ha_signin_session.go:90–105`). It pairs with the six-digit code the owner creates on another device (NOVA in Home Assistant, "Connect a device"). The default Linux profile falls back to a private key file when there is no Secret Service. A named profile, or a keyring that is present but locked, can still stop there (`cli/device_credential_storage_probe.go:63–83`). Starting a Home Assistant Link sign-in still needs a desktop (`cli/setup_cloud.go:128–138`), so a bot host without a browser pairs locally with the code.
2. **The one-click question isn't asked there.** It needs a window and a desktop key store (`ownComputerHere`, `cli/setup_own_computer.go:33–37`), and a code pairing never declares the computer anyway.
3. **The phone is offered only in narrow cases.** The terminal wizard calls `offerPhoneLink` at the end (`cli/setup_flow_finish.go:300–309`), but only when this run paired, setup is interactive, and Link isn't paused. In offer mode it stays silent when the phones can't be read (`cli/confirm_phone_link.go:86–96`). A re-run on a computer that's already paired, `ha-nova pair`, and a scripted setup offer nothing and name no next step.
4. **A risky action** opens an ask on the App. With no phone linked, only the page can approve it, but the agent still says "Confirm on your linked phone or in Home Assistant (NOVA)" (`say.relay_ask`).
5. **A Mac with no monitor and a logged-in user** counts as having a window (`launchctl managername` is `Aqua`), so the waiting window opens on a screen nobody sees. A code pairing can't confirm there, so it's harmless, but it doesn't help.

## What changes

### 1. The phone is offered wherever this computer can't confirm in its window

- **Who gets the offer:** any interactive `ha-nova setup` run, including a re-run on a computer that's already paired, and `ha-nova pair` in a terminal, when no phone is linked for this computer and its window can't confirm. That covers: no window here, a code pairing, a no to the one-click question, or `/gate/v1/me` saying the window is off. On a computer whose window confirms, nothing changes: the overview keeps its phone row.
- **Words (terminal):** "Confirm risky changes (doors, alarm, deletes) on your phone? HA NOVA sends one notification to the phone you pick; tap Allow there." Then today's `choosePhone` menu (numbered without arrow keys). Skip is the default, because Enter never sends a notification. The link ask and tap are today's (`/gate/v1/phone`, phone-only approval). The App stores the link for this computer.
- **No silent skip:** when the phones can't be read, or the App signs in as the owner, the offer says so in one line and names `ha-nova setup confirm-phone`, as the command does outside the wizard.
- **Without a terminal** (piped or scripted setup, or the bot running setup), nothing is asked. The result's `next_step` gives the commands for this profile word for word, so a bot can pass them on: `ha-nova setup confirm-phone list`, then `ha-nova setup confirm-phone "<name>"`, with `--server <name>` for a named profile. The person then taps Allow on that phone.
- **After a skip,** setup says where risky changes are confirmed now, effect first: "Without a phone, risky changes from this computer wait for the NOVA page in Home Assistant." If the App offers chat codes (§3), it adds: "Or the Home Assistant owner can let this computer confirm with a four-digit code in your AI chat, on the NOVA page. Your AI assistant sees that code too."
- **Key store:** a named profile or a locked keyring on a computer with no desktop session offers the private file in the same run, with today's warning and explicit consent, and doesn't send the person to a second command. An existing Keychain key is never copied (0.32 §5.4).
- **A lost or replaced phone:** changing the link is confirmed on the linked phone. If that phone is gone, the owner removes this computer on the NOVA page and pairs it again with a new code. A code pairing doesn't inherit the old link, so setup then offers the new phone. Setup and `docs/reference/client-integration.md` say so.

### 2. The bot says what the person can actually do

- **At plan time,** `GET /gate/v1/me` gains `phone: true|false` (a phone link is stored for this computer) and `code` (§3). They are hints for the plan's `say`. A stored link can still be paused or over its hourly cap.
- **While waiting,** the text follows the ask's actual `channels` and the worker's localized button. With `phone` in `channels`: "Tap “{button}” in the HA NOVA notification on your phone. Or confirm on the NOVA page." `{button}` is the phone's own action button, so for an unlock the bot says "tap Unlock on your phone". Without `phone`: "Confirm on the NOVA page in Home Assistant." If no phone is linked, it adds "To confirm on your phone, run ha-nova setup confirm-phone on this computer." Where the 0.32 window contract applies, its window-first copy stays. A failed or paused phone never makes the App offer a code.
- **Before PR 2** (the App's `phone` field), the CLI-only text stays conservative: "Confirm on your phone if one is linked to this computer, or on the NOVA page in Home Assistant." It never says "your linked phone" without knowing one is there.
- **Skills:** `skills/ha-nova/SKILL.md` keeps "a code only where `say` shows one", and adds one sentence: pass `say` on word for word, never type a code yourself, and never send a code that a tool printed. Word budgets stay ratchets.

### 3. The chat code, for a computer whose owner picks it

**How this computer confirms is one owner-chosen mode.** Each computer row on the NOVA page offers the owner one choice: "One click in a window here" (0.32), "A code in the AI chat", or neither (phone or page). The two are mutually exclusive in the App: turning the code on turns the window off in the same registry write, and turning the window on turns the code off and ends waiting code asks. A locked or absent display never switches modes. That also gives an unattended Mac a reliable setting: the owner picks the code, or neither.

- **Only the Home Assistant owner turns it on,** on the NOVA page, with the window switch's protections: fresh `checkOwner`, CSRF-guarded POST, logged with the user id. It is off by default, a new pairing starts off, and it is revocable at any time. Under the choice, verbatim: "For a computer nobody sits at. The code appears in your AI chat, so the assistant sees it too: HA NOVA can't tell whether you typed it, the assistant did, or another program using this computer's key. Use a private chat only you can write in. A linked phone is safer."
- **At the owner's pairing visit:** the new computer's row appears live on the NOVA page where the owner just created the six-digit code, and the hint under the code says "After pairing, choose here how this computer confirms." No terminal yes and no possession of the pairing code turns it on. A code pairing has no owner session on the computer, so neither could show that the owner chose it.
- **A Link computer** may only be opted in by the owner for a device whose Link user is that owner, as for the window.

**The App's consent record.** `codeConfirm: {userId, atMs, rev}`. `userId` is the owner who opted in. `rev` rises on every change of this computer's confirm mode or phone link. Eligibility, checked by the App at open and again at the code:

- a paired-device principal with an active registry record (never the shared token, the chat bridge, the gate worker, or the standalone container);
- `codeConfirm` is set, and a fresh `config/auth/list` shows its `userId` as the active, non-system owner. Another owner after a transfer hasn't opted in, so no code. A failed read means no code;
- no phone link is stored for this computer. Linking a phone ends the code without another step, and the phone is the path again (H1);
- for a `keychain` record, `legacyCleanup` is `"complete"` (0.32 §1);
- any key store, a file included: whoever holds the key can already use the code (see the limit below).

`/gate/v1/me`'s `code` is `on` when all hold, `phone` when only a linked phone stops it, `owner` when the owner read fails, and `off` otherwise.

**Where the code works: the shell path, the plan's first App ask.** H2 covers `ha-nova apply` run by a bot. Stdio MCP's `ha_apply` doesn't carry a code in 0.33. It confirms on the phone or the page and says so, and `docs/reference/client-integration.md` names that limit. The code answers only the ask that the plan's rechecked apply opens. A later hold inside the same apply (`sendWrite`) doesn't take it: the CLI says what already ran and asks for the phone or the page.

**The flow.**

1. `plan` stores a relay plan as today. Its `say` shows the full preview, every item of a batch included, and ends: "To confirm, run the step; HA NOVA then shows a four-digit code here for you to type back."
2. `apply` opens the ask with `accept_code: true`. The CLI sends it only to an App whose `/health` advertises `code: 1`. When eligibility holds, the App snapshots `rev`, draws four random digits (`crypto.randomInt`), keeps them with the ask, and returns `code` only in this open answer to this principal. It never returns the code from `wait`, the page, the live feed, or a link ask. The direct TLS answer is marked `no-store`. The digits never appear in errors, logs, the audit log, or the CLI's ask sidecar.
3. `apply` returns at once with `waiting_for_approval`. It saves the exact plan and ask binding (0.32 §6), and `say` is: "To confirm the {n} step(s) shown above, type this code in the chat: {code}. It works for {seconds} more seconds. Your AI assistant sees it too." `next_step` tells the agent to end its turn, wait for the person's next message, and send only a reply that is exactly four digits, as `ha-nova apply --confirm <code> --plan <id>`. With `--confirm` first, a configured client permission prompt still applies (`cli/claude_apply_rule.go:16–23`). The agent asks for no extra yes.
4. With `--confirm`, the CLI joins only that saved ask and sends `{ask_id, op: "code", code}`. It never opens another ask and never resends the digits against a different ask. A first or second wrong code, or a retryable error, keeps the plan and its binding. Cancellation, expiry, and an unknown outcome are three different answers.
5. The App compares four ASCII digits against the ask's code and counts the attempt. Then it re-reads the owner (the only wait). After that, synchronously and with no wait in between, it re-reads the active record and the phone link, compares `rev` with the snapshot, and settles in the same `settle` the phone, page, cancel, and expiry use. The grant is the 0.30 grant: exactly the shown requests, once, within 2 minutes. The 0.31 recheck and the sends follow as after a phone tap. Answers: a wrong code gets `409 GATE_CODE_WRONG` (the third one cancels the ask); a changed mode, owner, link, or device gets `409 GATE_CODE_OFF`; a failed owner read gets `503 GATE_UNAVAILABLE`. Nothing is approved in any of these. An ask that already ended answers with its terminal state, never a second grant. The per-computer limits on opening asks stay.
6. **Turning the code off** ends waiting code asks. A grant already given runs within its 2 minutes, like a phone OK, and the page says so.
7. The page lists the approval under recent confirmations as "confirmed with a chat code on {computer}".

The three minutes run from the open, so an away person who answers late runs the step again for a new code. The two applies are two tool calls, not two approvals.

**No bypass.** No flag, environment variable, setting, or tool argument confirms in the CLI. A grant exists only from the App's `op: "code"` answer. The CLI never compares or derives the code. These App codes are separate from the CLI's HMAC codes for local and bridge plans (`cli/confirm_code.go:18–26`), which don't change.

**Older versions fail closed.**

| Pairing | Result |
|---|---|
| 0.33 CLI, App before 0.33 | no `code: 1`, so no `accept_code`: phone or page, as today |
| CLI before 0.33, 0.33 App | the open carries no `accept_code`, so the App offers no code |
| rollback to an App before 0.33 | it ignores the field and offers no code. Its next registry write drops the field. Without a write, the consent stays on disk and a later upgrade honors it again, still bound to that owner and checked as above. A rollback to an App without the gate is stopped by the CLI's `gate_seen` (0.30) |
| a `code` the CLI didn't ask for | ignored |

**The honest limit** (`docs/reference/safety.md`, `docs/reference/client-integration.md`, setup's line, the NOVA page text): the code is shown in the AI chat and the tool transcript, and it passes through a command line. So the AI assistant sees it, and an assistant that's told to, for example by a prompt injection, can type it itself. So can any program that uses this computer's key, from any device that has a copy, and anyone else who can write in that chat. For such a computer, the code shows that someone took the step in the chat, not that the person did. A linked phone is the confirmation only that person can give. That is why the code is off by default, only the owner turns it on, it excludes the window, and a linked phone ends it. Chat apps (S6–S8) are unchanged: their codes stay as in `docs/reference/chat-apps.md`.

## Relay budget

The App changes: the consent record with its validation, the owner's mode choice and its mutual exclusion with the window, the hint at pairing, the eligibility check with the revision snapshot and the Link-user rule, `accept_code` and the code on open with `no-store`, `op: "code"` (sharing the window op's settle, log, and error path) with its attempt counter, the `/gate/v1/me` fields, and `/health` `code: 1`. That's about **120 lines**, above today's ceiling of 14,410 (now 14,408). The Relay stays dumb: it draws and compares a code and checks an owner's recorded choice. Rating, wording, and the agent's texts stay in the CLI and the catalog. **This needs a ceiling raise to about 14,530, which is the maintainer's decision, before the build.** Without it, H2 doesn't ship, and only §1 and §2 (CLI, conservative text) go in.

Rejected:
- **Reuse the window switch,** with the CLI showing a chat code and reporting `op: "window"` (0 Relay lines). The App couldn't tell a click from a chat code. The owner's "one click in a window" would silently turn into "the AI sees the code". File keys stay excluded from the window. And the page would log a code as a window confirmation.
- **A CLI-minted code with the App checking only the switch.** The App couldn't enforce the attempt budget or bind the code to one ask.
- **A setup yes on the computer.** A code pairing proves no owner at that terminal.
