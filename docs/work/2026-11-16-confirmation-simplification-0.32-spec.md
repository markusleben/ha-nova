# Confirmation simplification for 0.32: the owner's own computer confirms in its window

Status: active (built only after the maintainer's go)

Date: 2026-11-16. Owner: the Relay's safety check (`nova/src/http/gate-asks.ts`, `nova/src/http/gate-owners.ts`, `nova/src/http/handlers/nova-approve.ts`, `nova/src/http/handlers/nova-page*.ts`, `nova/src/security/device-registry*.ts`, pairing v1/v2), the CLI's gate client and window (`cli/gate_client*.go`, `cli/confirm_window*.go`, `cli/confirm_strings.*.json`), pairing and setup (`cli/pairing_*.go`, `cli/setup_*pairing*.go`), macOS key storage (`cli/keyring_darwin*.go`, `cli/native_secret_worker*.go`, `cli/device_credential_migration.go`), the update (`cli/command_update.go`), the tier engine for MAR-209 (`cli/tier_*.go`), the skills' confirmation wording, and the macOS release signing (`scripts/release/build-sign-darwin-binaries.sh`, `scripts/release/verify-macos-signature.sh`). Target: the 0.32 train. High-risk: security, a change to the 0.30 gate's contract, release machinery.

## Why

HA NOVA asks for an OK in eleven different ways today, and since 0.30 the window on the computer shows a risky change but can't confirm it (`docs/reference/safety.md`, the "safety check" row). Markus finds the system too complicated and wants the window back as the normal place to confirm on his own computer, on every OS. His decisions (2026-11-16):

- D1: the window OK is **on by default on macOS, Windows, and Linux** for the owner's own computer.
- D2: an existing computer gets it **by pairing once more** (about a minute); that also retires keys an older release may have copied.
- D3/D4: everything ships **together in 0.32**; **chat apps must keep working in every setup that works today**; the four-digit codes **stay, as a last resort** where no other way exists.
- D5: the macOS binary gets a **new code-signing identifier** from 0.32.
- **Friction** ("so wenig nervig wie möglich ist mit den Bestätigungen"): a **hard acceptance criterion**, equal to "chat apps keep working". The friction budget below sets the targets, counts every scenario today and after 0.32, names every ask that stays above target and why, and the 0.32 release PR carries a test bed count of the asks per scenario.

This deliberately changes the 0.30 gate's promise (`docs/work/2026-11-03-relay-typed-gate-spec.md`, Threat model: "no typed-tier effect reaches Home Assistant from a device credential without a person's approval that the Relay verified"). For the key of a computer the owner declared as their own, with the window switch on, the App accepts the computer's own report that its window was confirmed. The App can't verify that a person clicked.

## What a user sees

1. **Setup asks once, right after the owner's Home Assistant sign-in and before this computer pairs**, with yes as the default (the setup page: a switch, on, under the sign-in button; the terminal: Enter is yes). Its words say what it does, not who owns what (Markus, 2026-11-16): the terminal asks "Confirm risky changes (doors, alarm, deletes) here with one click in a window? Only say yes if nobody else uses this computer.", and after a no says "OK. Risky changes on this computer are confirmed on your phone or the NOVA page."; the setup page's switch reads "Confirm risky changes here with one click", with the hint "Only if nobody else uses this computer. Otherwise you confirm on your phone or the NOVA page." It appears only where the Home Assistant **owner** signs in during setup, only when the App approves in a computer's window (`window: 1` in `GET /pair/v1/info`, readable before pairing, and in `/health`), never for a file key, and on a Mac only once its old sign-in cleanup reports complete (§5.3). Without a terminal (piped or scripted setup) nothing is asked or declared. Re-pairing a computer (D2) and the Mac re-pair after the update ask the same question. A six-digit-code pairing, a Link pairing, and any setup that didn't ask start unticked; the owner turns it on with one click on the NOVA page ("Turn on").
2. **A risky change on that computer** (unlock, open a door, gate, or garage, disarm, delete, file writes, and everything else a plan rates typed) opens the usual window with the change as a question ("Kellertür entriegeln?"), the list, [Confirm] and [Cancel] (on Windows: "OK confirms this change"). The chat says the same ("Confirm in the window on this computer"). The NOVA page lists it at once. The linked phone asks at once when nobody is at the computer (no input for 20 seconds, or the screen is locked), else only after 60 seconds. The first answer counts.
3. **After a window OK**, the phone shows one silent line per computer (no sound, no buttons; iOS passive, Android low importance) that each new OK replaces: "Confirmed in the window on <computer>: <title>". If the phone had already asked, a buttonless note and clear withdraw that question; iOS can retain its buttonless line alongside the stable note. The NOVA page lists every one under "Recent window confirmations".
4. **On the NOVA page**, every computer row shows "Confirm with one click on this computer": On / Off / why not, with one owner-only Turn on / Turn off button and, under it, the hint "Only if nobody else uses this computer. Otherwise you confirm on your phone or the NOVA page." and the warning: "Programs using this computer's key can approve without you, also from another device if the key is copied."
5. **Every other computer** (someone else's, a file key, a service install, an older pairing, the switch off) keeps today's behavior: the same window, saying "Confirm on your phone or on the NOVA page", with [Open in Home Assistant] and [Cancel], plus one line, effect first, why this window can't confirm ("One-click confirming needs this computer paired again once" / "One-click confirming isn't turned on for this computer; the owner can turn it on on the NOVA page" / "One-click confirming is turned off for this computer" / "One-click confirming needs this computer's old HA NOVA version signed out of Home Assistant first: run ha-nova setup --server <profile>"). The cleanup reason and retry are catalog-owned and also appear in the agent\'s `say`/`next_step`; ordinary actions continue through the phone/page and never start cleanup prompts automatically.
6. **Chat apps don't change** in 0.32: on the NOVA App the requester's linked phone, else a chat code at Manage everything where codes are on; on the standalone container the one phone linked to the container, and for the chat's own local plans (a dashboard delete, a skill-marked raw item) the chat's own check first, a code at Manage everything, then the container's phone if it holds a step (`docs/reference/chat-apps.md` lines 83–92, 126–129).
7. **Codes stay as the last resort**: a chat app user on the NOVA App without a linked phone, and, on a computer, a raw plan item typed only by a skill's mark where no window opens. On an App with the safety check a computer can't hear its phone's answers (`cli/gate_phone_move.go:22–31`), so that item uses a code even when a phone is linked, as today.

## Threat model change

Unchanged for: chat apps and the bridge, other people's computers, code pairings the owner didn't declare, file and service keys, the standalone container, and every request below typed.

New, for a computer the owner declared as their own with the switch on (stated in `safety.md` and on the NOVA page):

- **Windows (Credential Manager / DPAPI) and Linux (Secret Service):** every process of the same user reads the device key without a prompt. A script, malware, or an AI agent with a shell (for example after a prompt injection) can approve a risky change with that key and no click.
- **macOS (Keychain):** the key is bound to the signed `ha-nova` (from 0.32 by its new identifier, §5). Another program gets a Keychain prompt instead of the key; a program with Accessibility or screen control (automation tools, remote control, an AI's computer use) can click Confirm; a Keychain prompt the person allows hands the key out.
- **Home Assistant Link computers:** their owner's Home Assistant sign-in sits in the same store, so the App's check was never a boundary there (gate spec, decision 2); the window OK adds nothing a key holder couldn't already do.
- **Everywhere:** the App verifies the key, not the machine (`nova/src/security/principal.ts`), so a copied key approves from any device while the switch is on. An AI that only uses HA NOVA's own tools (MCP, `ha-nova` commands) can't confirm: no tool, flag, environment variable, or setting answers the window. The presence hint (§4) only changes when the phone asks, never what gets approved.
- **What still holds:** the OK covers exactly the requests shown, once, within 2 minutes (the 0.30 grant); the plan is checked again after the OK (0.31 ask-first); a Cancel that races an approval wins on the computer; nothing falls back to a weaker channel on an error.

## Design

### 1. Who is eligible (decided by the App)

A principal may confirm in its window only when **all** hold, checked at the moment of the window OK:

- kind `device` with a registry record (never the legacy shared token, the chat bridge's or the gate worker's reserved ids, or the standalone container's token: decided by the authenticated principal, never by a client label); local pinned and Link pairings both qualify;
- `ownComputer.userId` set, and a fresh read of `config/auth/list` shows that user as the active, non-system **owner** (an ownership change ends it; a failed read means no window OK; for a Link device, `cloudUserId` must be that same user);
- `credentialStore` is a desktop store (`keychain`, `credential_manager`, `secret_service`), recorded at pairing from the pairing CLI's report; never `file` (`--credential-store=file`, `setup --service`, no desktop keyring);
- `windowConfirm` is `true`.
- For a `keychain` record, `legacyCleanup` is `"complete"`; missing or `"pending"` means no window approval, even if its switch is on. This is the pairing CLI's report of verified cleanup, not an independent App check of Home Assistant's OAuth grants.

The store and the platform are the pairing CLI's own report. The App can't check them; the root of trust is a pairing the owner authorized. A record from before 0.32 has no `credentialStore` and no `ownComputer`, so it is never eligible: its window and the page say "Pair this computer again once to confirm here" (D2).

### 2. Registry and pairing (Relay)

- The pairing foundation adds `credentialStore?: "keychain" | "credential_manager" | "secret_service" | "file"`, `ownComputer?: {userId, atMs}`, and `windowConfirm?: boolean` to `DeviceRecord`; the Mac layer adds the cleanup field below. `validateDevice` checks them by type and value (unknown values: registry corrupt, as for other fields).
- The Mac layer also adds `legacyCleanup?: "pending" | "complete"`, carried from pairing metadata `legacy_cleanup` into the pending record and activation. A keychain pairing without a known complete report is ineligible. After exact revocation, the active device may send `op: "legacy_cleanup_complete"` on its authenticated ask route; this changes only its cleanup field, never its owner declaration or `windowConfirm`. It enables no shared/internal caller. Retry therefore requires no new device pairing. `/gate/v1/me` and the page return `legacy_cleanup_pending` while incomplete. Store provenance and cleanup reports have the same owner-authorized CLI trust boundary.
- Pairing metadata (v1 and v2) takes `credential_store` (one of the four values; missing = unknown, never eligible).
- `POST /pair/v2/arm` and `/pair/v2/arm/link` take `own_computer: boolean`. The arm is the owner's own authenticated ingress session (`checkOwner`, `pair-v2.ts:52–59`), so this is the owner's statement; the App stores the owner's user id with the pending pairing and writes `ownComputer` and `windowConfirm: true` at activation only when the stored store value is a desktop store. v1 code pairing never sets `ownComputer`.
- **Re-pairing keeps the phone.** A new pairing is a new device; activation retires the same-install predecessor. The Mac owner-bound retirement below replaces the old key-reading fallback in `cli/pairing_previous_device.go`. When the arm was the owner's, the App copies the revoked predecessor's `confirmPhone` to the new device in the same registry write, so the person doesn't link their phone again and no link ask precedes the first risky change. A code pairing copies nothing.
- **Older non-default profile identities:** some predecessors used the plain install id instead of today's profile-derived id. Before arming a replacement, the owner's fresh registry view identifies the explicit predecessor under either form, without reading its device key. Bind that predecessor to the owner-authenticated arm and pending record; activation atomically retires its old active/pending credentials and carries its phone as above. Never use an unauthenticated client-supplied predecessor to revoke a device. If several profile records make the predecessor ambiguous, ask the owner to select the old NOVA row rather than guessing. Verify the captured predecessor ids are absent from the fresh registry; negative credential proof runs with fixtures or the old signed binary only in the isolated lane, not by prompting the new binary to read a device item.
- Revoking a device ends everything.

### 3. The NOVA page (Relay)

- Each computer row: "Confirm with one click on this computer: On / Off" (an undeclared computer reads Off), or why not, effect first ("One-click confirming can't work on this computer: …" for a key kept in a file or another Home Assistant sign-in, "… needs this computer paired again once", "… needs this computer's old HA NOVA version signed out of Home Assistant first").
- **Owner only** (fresh `checkOwner`, CSRF-guarded POST, logged with the user id): one Turn on / Turn off button. Turn on of an undeclared computer sets `ownComputer` to the clicking owner and, with a desktop store, turns the switch on: one click (`window_mine`); otherwise it flips the switch (`window_on` / `window_off`). On a row that can't confirm, Turn off clears both (`window_not_mine`). Administrators see the state, can revoke the device as today, and can't turn it on.
- Turn on refuses a keychain device whose cleanup is missing or pending; it cannot clear that condition. The row names the pending old-sign-in cleanup and its retry step.
- The hint "Only if nobody else uses this computer. Otherwise you confirm on your phone or the NOVA page." and the warning text above, verbatim, under the button.
- "Recent window confirmations": the last 50, kept in `/data/gate/window-log.json` (time, computer, title), written with a rename; a write that fails is logged and doesn't block the OK.
- Texts come from `cli/confirm_strings.*.json` through the worker's `/texts` route, as the approval view's do.

### 4. The ask contract (Relay and CLI)

- `GET /health` adds `window: 1` on an App that has this contract. New `GET /gate/v1/me` (device principals) answers `{window: true|false, why}` with §1 checked now, so the CLI can word `say` and `next_step` at plan time.
- `POST /gate/v1/ask` (open) takes an optional `presence: "present" | "away" | "unknown"` (sent only to an App with `window: 1`) and answers `channels` with `"window"` added when §1 holds at open time. The CLI shows [Confirm] only then.
- New `{ask_id, op: "window"}` on the same route. The App re-checks §1 (fresh owner read), then, in the same synchronous state change that phone, page, cancel, and expiry use (`settle` in `gate-asks.ts`; the first terminal state wins), marks the ask approved through the window and answers `approved {grant_id, until}`. Another principal's or an unknown id: `404 GATE_ASK_UNKNOWN`. An ask already ended: its terminal state, never a second grant. §1 not met: `409 GATE_WINDOW_OFF`; a failed owner read: `503 GATE_UNAVAILABLE`. In both, nothing is approved and the ask stays open for the phone and the page.
- New `{ask_id, op: "away"}`: the CLI reports that the person left (20 seconds without input, or the screen locked) while the window waits.
- A link ask (`/gate/v1/phone`) can't be approved through the window.
- New `{op: "window_off"}` (device principals only) sets the caller's own `windowConfirm` to `false`. No device route turns it on.
- **When the phone asks, with a window offered:** at once on `presence: "away"` or a later `op: "away"`; after 20 seconds on `"unknown"` (Linux, where HA NOVA has no idle reading); after 60 seconds on `"present"`. The CLI sends `presence` only when this invocation will actually show the window; a chat app, an SSH session without a display, or a window turned off locally sends none, and without `presence` the phone asks at once. The ask keeps its absolute 3-minute deadline; the phone waits for what is left. The page shows the ask at once. A delay never removes a channel, and a failed window still leaves the phone and the page. Presence comes from the computer and is not trusted for anything else: a lying client can only delay its own owner's phone.
- **After-note:** (1) the App settles the ask synchronously with its winning outcome, so nothing else can win after; (2) for a window winner with a linked phone, it calls `POST /phone/end {ask_ref, seq, outcome: "window", link, lang, title, computer: {id, name}}` on the authenticated worker and waits for its answer, at most 3 seconds; (3) only then it hangs up the `/phone` request (which now carries the same 64-lowercase-hex `ask_ref`). The same end route covers a phone that was never asked; there is no separate `/notice`. The worker keeps at most 1,024 four-minute lifecycle entries. An end before registration prevents the question; an end during a send is retained until the phone call unwinds; a late tap cannot replace the App's winning outcome; a duplicate end is a no-op. A normal result already in flight is followed by the window correction. Question cleanup uses the question's random tag, never the stable note's tag. The note uses `ha-nova-window-<hash of computer id>`, so renaming a computer does not stack notes. Its catalog keys are `phone.window.*`, with names through `sayText`; it states the computer and action, without a cosmetic daily counter or time-zone state. iOS uses passive delivery; Android uses the low-importance `HA NOVA confirmations` channel. The App assigns each window win a strictly increasing positive sequence number in its process/worker epoch. The worker serializes delivery per computer and updates its latest stable note only for a higher sequence, so a delayed older request cannot replace a newer note. Each end has its own three-second recording budget; no App-side queue is needed. Other outcomes keep the existing withdrawal/result path. A failed or late end: the App hangs up anyway, the worker withdraws as today, and the failure is logged. The App appends to the window log either way. Best effort: no delivery failure undoes the OK, and an iOS clear can fail, leaving the old buttonless question note alongside the stable note. With no phone linked, only the log shows it.
- **Pause and limits:** a window approval counts as a person's answer and resets the unanswered count, like a page approval. An ask counts as unanswered on the phone only if its phone ask was actually sent and stayed out at least 15 seconds (today: 15 seconds of ask-open time, `nova/src/http/gate-owners.ts:80–89`). The hourly limit protects the phone, not the window: past 10 asks in an hour, a computer's next ask opens **without the phone** (window and page only), as during a pause; a hard cap of 60 asks an hour per computer (`429 GATE_ASK_LIMIT`) protects the App.
- Wire values are closed sets: `window` in `channels`, `presence`, `GATE_WINDOW_OFF`, and the ops ship in the same App release as the CLI that sends them.

The worker reports accepted notification delivery by flushing `X-Ha-Nova-Phone-Sent: 1` on the authenticated `/phone` response before its final JSON answer. This means Home Assistant accepted the question, not that a physical phone displayed it. The App starts exposure time only on that signal from its current worker and only while the same ask is waiting. Its phone quota reserves one identity-bound entry per dispatch; only a final `not_asked: true` releases that entry, even if the ask ended meanwhile. The worker sets that field only when no notification send, including a preceding clear, started. Failed sends, malformed answers, timeouts and hangups remain charged because delivery is uncertain. Link asks use the same tracking and keep their existing phone-only approval flow. A phone over its hourly cap answers like a paused phone (`429 GATE_PAUSED` when no other channel is left, so existing callers such as the automatic phone move continue on the window or page). The standalone shared-token hard cap stays at ten asks per hour; the sixty-ask cap applies to paired computers. The recent-50 log ships with its page reader, and `/health` advertises `window: 1` only after the whole contract is implemented.

### 5. macOS: keep the key where only the new `ha-nova` reads it (CLI and release)

Needed for the macOS statement; Windows and Linux gain nothing from it, since every same-user process reads their key.

1. **New signing identifier.** `SIGNING_IDENTIFIER` in `scripts/release/build-sign-darwin-binaries.sh` and the check in `verify-macos-signature.sh` change from `com.markusleben.ha-nova.cli` to `com.markusleben.ha-nova.cli2` (same Developer ID team). New Keychain items trust only binaries with the new identifier, so no earlier release reads them silently, even with `HA_NOVA_KEYRING_SERVICE` (`cli/keyring_service.go:36–40`).
2. **New slots.** The new binary can't read items the old identity created without a Keychain prompt, and today's setter modifies an existing item in place, which keeps its old ACL (`cli/cloud_oauth_secret_darwin_api.go:157–202`). So 0.32 writes to new slots under a root no legacy slot can have: `com.markusleben.ha-nova.cli2/<kind>/<profile>`, kinds `device`, `device-pending`, `relay-token`, `link-current`, `link-pending`, `link-retiring`, the profile name percent-encoded (legacy slots all start with `ha-nova`, `cli/device_credential_store.go:47–58`, `cli/cloud_oauth_secret_store.go:14–18`; a suffix such as `.v2` would collide with today's slot for a profile named `v2`). Each slot keeps two generations (`#1`, `#2`, each value led by its sequence number): a write adds the next generation fresh under the other name and only then removes the older one, so it never writes into an existing item, every item it writes trusts only the new identity, and a failed or cut write leaves the previous value readable. Reads and writes share a per-user lock (writers exclusive), so a read never lands between a write's add and its cleanup, two writes never interleave, and an exact delete compares and removes under that one lock.
3. **One re-pair after the macOS update, about one minute.** The shipped updater replaces the bundle before running any new-binary code, so 0.32 does not promise a pre-switch migration or rollback on a declined sign-in. No bootstrap, fallback runtime, or bridge release is needed.
   - Ordinary reads never open a Keychain dialog for an old item: legacy lookups disable authentication UI. Missing or unreadable device credentials mean "not paired under 0.32", not a generic error or repeated prompt. During the one-time re-pair or an explicit person-started cleanup retry, an existing legacy Link OAuth current, pending or retiring envelope may ask for access if its exact grant cannot be identified otherwise. Never prompt for a device credential or a missing item. The catalog-owned introduction says macOS will ask for the password so HA NOVA can sign the old version out of Home Assistant: choose "Allow", not "Always Allow". Each explicit attempt may prompt once per still-needed item, never retrying automatically after denial. Typical cost: one prompt for a Link profile, none for a local-only profile; interrupted generations can require one per needed item.
   - On an owner Mac with a usable sign-in, the first command that needs its pairing returns a distinct needs-re-pair result with one next step: one Home Assistant sign-in, about one minute. That same flow asks once, before pairing, whether this is the person's own computer and binds the answer into the pending device; pending cleanup blocks its use separately until verified, so nobody is asked twice. It writes the new key directly into its new slot and carries the phone link over (§2). There is no second pairing step for the window OK. A denied or failed legacy cleanup leaves an ordinary paired device working, but the App must independently keep window eligibility off, including the page switch, until that profile's cleanup is verified. Return an explicit incomplete status and the person-started retry command `ha-nova setup --server <profile>`, which this flow makes work for every named local profile (today's guard refuses some, `cli/setup_named_profile_guard.go`); it resumes only cleanup, may prompt once per still-needed Link item, and does not re-pair the device again. Link sign-in state uses the disjoint generation slots too; missing or unreadable legacy state leads into this recovery flow without an implicit prompt; only the explicit exact-revocation step may prompt as above; already-created new-slot pending/retiring generations stay intact.
   - Activation retires the same-install predecessor's active and pending device credentials on the Relay, as today. An older non-default profile's row carries the plain install id instead, so the CLI retires it during the re-pair without reading the old key: the owner's sign-in arm names `previous_install_id`, and when exactly one active local row on that Relay matches, the arm answer returns its device id and name. The terminal asks once, naming the row (Enter is yes): another computer with a copied config, or this computer's default profile, may still use the plain id, so it is never retired without that answer. A pairing that can't ask (the setup page) leaves it and says the row is still listed. The pairing metadata then carries `retire_device_id`; the Relay keeps it only on that owner-armed pairing, and activation retires that exact row, with its install id's pending rows, only when it is active, local, not the App's own, and the new install id extends its id, in the same registry write, carrying its phone link over. A named profile whose key is gone re-pairs with `ha-nova setup --server <name>` by sign-in like the default profile, and the first command that needs the pairing says so ("this computer needs to be paired again … run: ha-nova setup [--server <name>]"; agents get the code `PAIR_AGAIN`). Setup for a named profile never reads, moves, offers, or writes the default profile's machine-wide relay token; its token step refuses with the pairing command. When the match is ambiguous, the answer is no, the pairing used a code, or the App predates the field, setup names the old row and the NOVA page step. A kept row doesn't block this computer's cleanup: it has no credential store, so it stays `pair_again`, and the window answers only its own device's asks, so it can't approve this computer's asks; it is never called revoked. This costs at most about 20 Relay lines (Captain, 2026-11-16: no larger predecessor contract). Verify rejection without prompting to read a device item. Cleanup is setup's last step for a paired Mac profile whose `/gate/v1/me` says `legacy_cleanup_pending` (the wizard and a completed setup's re-run, on terminal or page; the named-profile retry; Link-only setup), and its outcome line closes setup. macOS may ask only with a desktop session, outside service mode, in an interactive terminal or on the page, whose connect row shows the introduction; an unreadable `/gate/v1/me` counts as incomplete: for each legacy Link item (current, pending, retiring) under the profile's stable `profile_id` account, a copy kept by an earlier attempt is used first; otherwise the old item is read by its exact name without UI, then, only in that person-started setup, with one prompt after the catalog introduction. The exact envelope is validated and kept in a new-root copy slot (`link-legacy-<state>`) before revocation, revoked, and refresh must answer `invalid_grant`; only then does the device send `legacy_cleanup_complete`. Pairing sends no `legacy_cleanup` (missing means pending). Denial, an unreadable or corrupt item, a failed revocation, or a failed report leaves ordinary paired use working, the window off, and the retry command. A retry verifies kept copies again without asking for the old items. Never guess by a loopback client URL or delete a broad set of sign-ins. Old items stay in place; 0.32 never deletes or writes them. `uninstall --purge` revokes every profile's copies (Link or not), requires `invalid_grant`, and only then removes exactly those copies; a failure stops the purge with `config.json` kept for the retry. The App refuses every non-device bearer, so the old shared Relay token has no App access to rotate; standalone shared access is unchanged and never gets the window.
   - Before an agent starts the update, `check-update` and the update skill must explain that this Mac needs the person once to re-pair, so the agent asks first. The already-shipped CLI cannot acquire new preflight code: put "On macOS, 0.32 asks you to pair this computer again once." as the first sentence of the first `New Features` item, because its text notice chooses that headline before fixes and action items. Also put it under `Upgrade Notes`, which its JSON `release_highlights` exposes as an action item. Prove both paths with the 0.31 binary: `cli/release_digest_mac_repair_test.go` checks the body with the digest code, unchanged since v0.31.0, and `scripts/release/prove-old-cli-digest.sh` (workflow `old-cli-digest.yml`, on every change to the body) runs the published v0.31.0 Linux binary against it on a disposable runner. When release prep archives the body, both follow it to its archived path. After updating, including its `internal-offer-app-update` call, return needs-re-pair and the same single next step instead of a generic App-check failure.
4. **No copy to a file on macOS.** `migrateKeyringDeviceCredentialToFile` (`cli/device_credential_migration.go:51–100`) refuses on macOS when a Keychain key exists: While any server profile on the Mac holds a Keychain key, the install stays on the Keychain, which HA NOVA reads without a prompt: `setup --service` keeps the Keychain key and says so, and `pair --credential-store=file` refuses before using the code. Switching to files is install-wide and would hide every other profile's key (Link ones included) and the older-profile predecessor the re-pair must retire. A Mac with no Keychain key may still pair straight into a file, and that device reports `file`. **Windows and Linux:** the same commands keep copying the key into a file (no new pairing, so no break), but first send `window_off` for every profile they copy; if that fails, nothing is copied and the command says why. This guards the honest path only: there any same-user process can read the key anyway.
5. **The key goes only to its own Relay.** At pairing, the Relay's SPKI pin is stored in the same Keychain item as the key (`cli/device_pin_seal.go`). Every pinned send of a Keychain key (functional calls in `relayFunctionalTransport`, activation, revoke) refuses any pin other than the sealed one before it sends; a Keychain key without a pin (a Link key) never goes over a pinned connection. Every pinned send of a device key, on every OS, also refuses an address that isn't `https://`, since plain HTTP would skip the pin check. The address can stay in `config.json`: a different address can't pass the sealed pin. So editing `config.json` redirects nothing, and the refusal names the profile's repair command (`ha-nova setup`, or `ha-nova pair --server <name>` for a named profile). A pending key kept without its pin by an earlier 0.32 test build is never sent; the next pairing replaces it.
6. **`HA_NOVA_KEYRING_SERVICE`** on macOS only picks a relay-token slot under the new root, so it can never name a historic slot or another kind; the test and RC lanes keep using it to isolate a run.
7. **Inventory test.** A test (`cli/credential_reader_inventory_test.go`) lists every caller that reads the device key, a Link token, or the relay token, marks each as store plumbing, local-only, or sending, and fails on a new or vanished one. A package variable that holds a reader counts as a reader, so its callers are listed too. The transport rule is per credential kind: the device key goes only to the endpoint sealed with it; Link tokens go only through the verified Link ingress; a standalone shared Relay token keeps its configured transport, unchanged.

Honest limit kept: a person who allows a Keychain prompt for a program that isn't HA NOVA hands that program the key. A same-user program can plant an item under the new root before HA NOVA writes there, and HA NOVA may read it; that never hands the program HA NOVA's own key, because every write adds a fresh item and never writes into an existing one. Device re-pairing alone does not revoke legacy Link grants, so the window stays off until each is verified revoked. A 0.31 binary run again later can sign in to Link anew under the old items; that is the person's own new sign-in, which cleanup doesn't see once its copy exists. A same-user program can also steer the cleanup's inventory (an edited `profile_id`, a planted copy slot) and so get the window turned on while an old grant stays live; it gains nothing by that, because the same program can run the signed 0.31 binary and read those old grants without a prompt anyway. The window gate makes the honest migration finish; it isn't a barrier against code already running as the person. An ordinary paired device can continue working while cleanup is incomplete, but its window cannot approve.

### 6. The window, the wording, and the agent (CLI and skills)

- **One dialog everywhere.** The window shows the stored plan's own title and full prompt, built locally from `cli/confirm_strings.*.json` as a window plan's is today; the phone shows its short summary and the page the worker's items, from the same strings. macOS NSAlert, Windows `MessageBoxTimeoutW`, Linux zenity, unchanged (`docs/work/2026-11-10-wider-confirm-window-spec.md`).
- **With `window` in `channels`:** [Confirm] [Cancel]; footer "Your phone asks too if nobody answers here." (without a phone: "Or confirm on the NOVA page."). Confirm sends `op: "window"` and, with the grant, goes on as after a phone OK (the 0.31 recheck, then the sends). Cancel sends `op: "cancel"`. A phone or page answer closes the window. On `503`, Confirm retries quietly for up to 5 seconds; then, as on `409`, the window says "This computer can't confirm right now: confirm on your phone or on the NOVA page" and keeps waiting (the phone is asked at once).
- **A relay plan too long for the window** is never refused for that (today `windowTooLong` runs only for window plans, `cli/confirm_window.go`): the window shows the first items, "and N more: the full list is on the NOVA page", and no Confirm, since Confirm only approves what the window showed; the phone is asked at once.
- **Without `window`:** today's waiting window (`gate.window`, [Open in Home Assistant], [Cancel]) plus the one-line reason from `/gate/v1/me`. For `legacy_cleanup_pending`, catalog-owned copy says to finish signing the old version out and gives `ha-nova setup --server <profile>` as the explicit retry. The same reason and command appear in the agent's `say`/`next_step`; they never automatically start cleanup or add a chat confirmation on top of a phone/page answer.
- **Presence:** while the window waits, the CLI reads the idle time every 5 seconds (macOS `ioreg -c IOHIDSystem` `HIDIdleTime`; Windows `GetLastInputInfo`; Linux `unknown`), sends it with the open, and sends `op: "away"` once it passes 20 seconds. No new dependency, no cgo.
- **The agent says what the person sees.** With `window: true` from `/gate/v1/me`, `say` uses `say.window_ask` ("Confirm in the window on this computer. Not at the computer? Your phone asks shortly, or use the NOVA page."), `next_step` and `channelAsks` (`cli/confirm_code.go:108`, `cli/plan_store.go:197–209`) name the window, and the waiting answer of `ha-nova mcp` uses `say.window_waiting` (`cli/mcp_stdio_apply.go:128`). Without it, today's texts.
- **No second ask for the same plan when the command's wait ends.** Today `ha-nova apply` cancels the App's ask when its own 90 seconds run out (`cliWindowWait`, `cli/gate_client.go`), so a later tap hits a dead ask and the next apply asks again. 0.32 leaves the ask open, keeps its id with the stored plan, and answers `waiting_for_approval`; the next `apply --plan <id>` joins the same ask (as `ha-nova mcp`'s job already does, `cli/mcp_stdio_apply.go:103–135`) and uses a grant that arrived meanwhile within its 2 minutes.
- No flag, environment variable, or tool argument confirms; the window's answer comes only from the window process's output, as today.
- **Setup:** the question from "What a user sees" 1, asked before the arm (browser and terminal flow), only on sign-in pairing; the CLI sends `own_computer` with the arm only after a yes, and `credential_store` with every pairing. Amended 2026-11-16 (Captain): the original placement on the step-3 "safety net" screen came after pairing, and declaring at pairing with a step-3 undo failed open (an interrupted or browser-only setup left the computer able to approve without the box ever shown).
- **`ha-nova setup confirm-window off`** also sends `window_off`; `on` turns the local setting back on and opens this computer's row on the NOVA page, where the owner turns the App's switch on.
- **Dashboard delete onto the App's ask** (computers only). A dashboard delete is one request the gate rates typed (`cli/gate_verdict_test.go:84`), so its plan takes channel `relay` and asks once, instead of this computer's window plus the App's second ask. Rooms plans (preview-level: the chat "yes") and raw items typed only by a skill's mark keep this computer's own ask (`gateChannel`).
- **Skills sweep** (behavior-changing, so an end-to-end agent run on the test bed): the confirmation wording becomes "your own confirmation: the window on your computer, your phone, or the NOVA page; a code only where `say` shows one" in `skills/ha-nova/SKILL.md:99`, `skills/write/SKILL.md:78`, `skills/maintenance/SKILL.md:50–55,95`, `skills/admin/SKILL.md:44–46`, `skills/updates/apps.md:29–31`, `skills/yaml-config/SKILL.md:37`, `skills/assist/SKILL.md:86`, `skills/ha-nova/batch-safety.md:67`, `skills/ha-nova/capability-answer.md:92`; `skills/dashboard/SKILL.md:60` passes `--confirm` only when the plan carries a code. The agent never asks in the chat on top of the window. Word budgets stay ratchets: trim, never raise.

### Asks that stay above the targets, and why

1. **S7 (no phone in a chat app): two asks, and Claude asks again each time the AI checks back while a change waits.** The AI can read a chat code, so Claude's own "Needs approval" prompt on "Run a confirmed change" is the only human check (`docs/reference/chat-apps.md:42`). Way out: link a phone, then "Always allow" everything (S6). Moving chat asks onto the NOVA page or adding a read-only wait tool would change the connectors' tools and flow, which 0.32 keeps unchanged (acceptance criterion).
2. **Dead ends in the chat:** below Manage everything without a phone, and the standalone container without a linked phone, refuse risky changes. No channel a person controls exists there; the refusal says how to link a phone.
3. **S3, S4, S5: the window can't confirm**, the person confirms on the phone or the page instead (still 1 ask, in another place). Someone else's key, a key from before 0.32, or no window. S3 ends with one re-pairing (one sign-in, offered by the update).
4. **A raw item typed only by a skill's mark on a computer without a window (S5) asks for a code, even with a phone linked.** A computer can't hear its phone's answers on an App with the safety check (`cli/gate_phone_move.go:22–31`). Rare: one rule is left behind that mark.
5. **One more ask after an OK** when the home changed in between (drift), or when a later step's grant expired (2 minutes after the OK). An OK covers exactly the requests shown, once.
6. **Large delete batches:** an App ask holds 20 requests and a batch at most 20 plans, and apply sends no reload after a delete (Home Assistant's delete hook stops the item), so a full batch of deletes is one ask. A batch too long for the window is confirmed on the phone or page (§6).
7. **"Unlock for 5 minutes" is two asks:** the re-lock automation is a bigger change (chat yes) and the unlock is risky (window click). They are separate tiers in one preview; one OK for both would need grouped asks across tiers, a later change.
8. **One-time steps:** on a Mac, one re-pair after the 0.32 update (§5.3), with no device-key prompt and only the needed exact-Link-revocation prompts; the code-pairing fallback additionally links the phone once; on a computer from before 0.30 that never moved its phone link, a link ask before the first change's ask.
9. **Phone pause:** after five asks in a row go unanswered on the phone, it stays quiet for 5 minutes (window and page still work); past 10 asks an hour the phone is skipped; past 60 an hour a computer's asks are refused.
10. **The chat app's own first-time prompts** per tool (Claude, ChatGPT; and Codex's or Antigravity's own command approvals, for which setup adds a rule only for Claude Code, `cli/claude_apply_rule.go`) come from the client, not HA NOVA; they're measured in the client lane.
11. **S8 dashboard delete (standalone container): a chat code and then the container's phone.** Chat flows stay unchanged in 0.32.

### MAR-209: a service-call listener makes every action risky

On Markus's home a light call is risky: `automation.rolladen_watchdog_dynamische_cover_gruppen` triggers on every `call_service` event (no domain filter), and its script `script.rolladen_watchdog_check_group` calls `cover.open_cover`, `close_cover`, and `set_cover_position` with templated targets. That is correct and fail-closed today, and it makes every action in that home ask.

Approved fix (D6, Markus, 2026-11-16): **rate an unresolved target by every entity it could pick.** For a call whose target the CLI can't resolve (a template), it lists every entity that call's domain could address in this home, from the live state list (which also has YAML entities without a unique id, not only the registry), and rates each one as if the call named it, with the existing rules unchanged: unknown, custom, or missing cover classes count as doors; template and command platforms, groups, `switch_as_x`, scripts (an unresolved `script.turn_on` walks every script), and device siblings are followed as today (`cli/tier_engine.go:300–345`, `cli/tier_walk.go:109–117`, `cli/tier_rules.go:203–225`). Only when every candidate rates below risky and every read succeeded does the unresolved target stop making the call risky; any unknown candidate, failed read, or `calls.unknown` keeps it risky, and every other risky reason stays. It applies only to calls in the same run that follows the plan's own call, with no `delay`, `wait_template`, `wait_for_trigger`, or step that creates or reloads entities before them. A config save (an automation or script stored to run later, drafts included, `cli/plan_config.go:425–449`) and every later or delayed call keep today's rating, because entities added later would never be checked. The change lands in the shared classifier, so the App's check follows; negative fixtures (a template cover classed blind whose action unlocks, an unresolved script target that reaches an unlock, a YAML cover without class, a delayed call, a save) pin it in both the CLI's tests and `gateVerdict`'s, since parity alone could repeat the same wrong answer twice. `RUN_EVENT_LISTENER_UNEXPLAINED` gets the same bound only if the bed copy of the watchdog shows it comes from the same calls. Stated honestly: "no risky effect in the model HA NOVA checks"; physical wiring HA NOVA can't see (a light relay that is really an opener) stays outside it, as today. As built (PR 7b): "before them" is decided once for the whole cascade after its service-call listeners, so any delay, wait, reload or create step, `remote.send_command`/`learn_command`, consumer `for:` (also `options.for`), scheduled trigger, or timer anywhere keeps every bound typed; a templated payload keeps the call typed too; only `plan call` and the App's check of a service call bound, every other check keeps today's rating.

If Markus's home does have an access cover the watchdog can pick, the bound doesn't clear it, and S1 there costs one window click per light (no phone buzz while he's at the computer). The next option (D7, not built unless needed): the owner acknowledges a specific automation or script version on the NOVA page ("this never opens <garage door>"), pinned to its config hash and dropped on any edit; it lowers only that automation's unresolved cover targets, never a lock, the alarm, or an access entity it names. It rests on a person's promise about a template, so it is weaker.
