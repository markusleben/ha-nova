# Confirmation simplification for 0.32: the owner's own computer confirms in its window

Status: active (built only after the maintainer's go)

Date: 2026-11-16. Owner: the Relay's safety check (`nova/src/http/gate-asks.ts`, `nova/src/http/gate-owners.ts`, `nova/src/http/handlers/nova-approve.ts`, `nova/src/http/handlers/nova-page*.ts`, `nova/src/security/device-registry*.ts`, pairing v1/v2), the CLI's gate client and window (`cli/gate_client*.go`, `cli/confirm_window*.go`, `cli/confirm_strings.*.json`), pairing and setup (`cli/pairing_*.go`, `cli/setup_*pairing*.go`), macOS key storage (`cli/keyring_darwin*.go`, `cli/native_secret_worker*.go`, `cli/device_credential_migration.go`), the update (`cli/command_update.go`), the tier engine for MAR-209 (`cli/tier_*.go`), the skills' confirmation wording, and the macOS release signing (`scripts/release/build-sign-darwin-binaries.sh`, `scripts/release/verify-macos-signature.sh`). Target: the 0.32 train. High-risk: security, a change to the 0.30 gate's contract, release machinery.

## Why

HA NOVA asks for an OK in eleven different ways today, and since 0.30 the window on the computer shows a risky change but can't confirm it (`docs/reference/safety.md`, the "safety check" row). Markus finds the system too complicated and wants the window back as the normal place to confirm on his own computer, on every OS. His decisions (2026-11-16):

- D1: the window OK is **on by default on macOS, Windows, and Linux** for the owner's own computer.
- D2: an existing computer gets it **by pairing once more** (about a minute); that also retires keys an older release may have copied.
- D3/D4: everything ships **together in 0.32**; **chat apps must keep working in every setup that works today**; the four-digit codes **stay, as a last resort** where no other way exists.
- D5: the macOS binary gets a **new code-signing identifier** from 0.32.
- **Friction** ("so wenig nervig wie möglich ist mit den Bestätigungen"): a **hard acceptance criterion**, equal to "chat apps keep working". The friction budget below sets the targets, counts every scenario today and after 0.32, names every ask that stays above target and why, and the 0.32 release PR carries a test bed count of the asks per scenario.

This deliberately changes the 0.30 gate's promise (`docs/work/2026-11-03-relay-typed-gate-spec.md`, Threat model: "no typed-tier effect reaches Home Assistant from a device credential without a person's approval that the Relay verified"). For the key of a computer the owner declared as their own, with the window switch on, the App accepts the computer's own report that its window was confirmed. The App can't verify that a person clicked.

## What a user sees

1. **Setup asks once, on the screen that already asks about phone confirmation** ("Choose your safety net"), a box ticked by default: "Only I use this account on this computer: confirm risky changes here in the window" (DE: „Nur ich benutze dieses Benutzerkonto auf diesem Computer: riskante Änderungen hier im Fenster bestätigen“). It appears only where the Home Assistant **owner** signs in during setup. A six-digit-code pairing starts unticked; the owner turns it on with one click on the NOVA page ("This is my computer").
2. **A risky change on that computer** (unlock, open a door, gate, or garage, disarm, delete, file writes, and everything else a plan rates typed) opens the usual window with the change as a question ("Kellertür entriegeln?"), the list, [Confirm] and [Cancel] (on Windows: "OK confirms this change"). The chat says the same ("Confirm in the window on this computer"). The NOVA page lists it at once. The linked phone asks at once when nobody is at the computer (no input for 20 seconds, or the screen is locked), else only after 60 seconds. The first answer counts.
3. **After a window OK**, the phone shows one silent line per computer (no sound, no buttons; iOS passive, Android low importance) that each new OK replaces: "Confirmed in the window on <computer>: <title>". If the phone had already asked, a buttonless note and clear withdraw that question; iOS can retain its buttonless line alongside the stable note. The NOVA page lists every one under "Recent window confirmations".
4. **On the NOVA page**, every computer row shows "Confirm in its window": On / Off / why not, with an owner-only switch and, under it: "Programs using this computer's key can approve without you, also from another device if the key is copied."
5. **Every other computer** (someone else's, a file key, a service install, an older pairing, the switch off) keeps today's behavior: the same window, saying "Confirm on your phone or on the NOVA page", with [Open in Home Assistant] and [Cancel], plus one line why this window can't confirm ("Pair this computer again once to confirm here" / "Not marked as your computer" / "Turned off on the NOVA page").
6. **Chat apps don't change** in 0.32: on the NOVA App the requester's linked phone, else a chat code at Manage everything where codes are on; on the standalone container the one phone linked to the container, and for the chat's own local plans (a dashboard delete, a skill-marked raw item) the chat's own check first, a code at Manage everything, then the container's phone if it holds a step (`docs/reference/chat-apps.md` lines 83–92, 126–129).
7. **Codes stay as the last resort**: a chat app user on the NOVA App without a linked phone, and, on a computer, a raw plan item typed only by a skill's mark where no window opens. On an App with the safety check a computer can't hear its phone's answers (`cli/gate_phone_move.go:22–31`), so that item uses a code even when a phone is linked, as today.

## Threat model change

Unchanged for: chat apps and the bridge, other people's computers, code pairings the owner didn't declare, file and service keys, the standalone container, and every request below typed.

New, for a computer the owner declared as their own with the switch on (stated in `safety.md` and on the NOVA page):

- **Windows (Credential Manager / DPAPI) and Linux (Secret Service):** every process of the same user reads the device key without a prompt. A script, malware, or an AI agent with a shell (for example after a prompt injection) can approve a risky change with that key and no click.
- **macOS (Keychain):** the key is bound to the signed `ha-nova` (from 0.32 by its new identifier, §5). Another program gets a Keychain prompt instead of the key; a program with Accessibility or screen control (automation tools, remote control, an AI's computer use) can click Confirm; a Keychain prompt the person allows hands the key out.
- **Home Assistant Link computers:** their owner's Home Assistant sign-in sits in the same store, so the App's check was never a boundary there (gate spec, decision 2); the window OK adds nothing a key holder couldn't already do.
- **Everywhere:** the App verifies the key, not the machine (`nova/src/security/principal.ts`), so a copied key approves from any device while the switch is on. An AI that only uses HA NOVA's own tools (MCP, `ha-nova` commands) can't confirm: no tool, flag, environment variable, or setting answers the window. The presence hint (§4) only changes when the phone asks, never what gets approved.
- **What still holds:** the OK covers exactly the requests shown, once, within 2 minutes (the 0.30 grant); the plan is checked again after the OK (0.31 ask-first); a Cancel that races an approval wins on the computer; nothing falls back to a weaker channel on an error.

## Design

### 1. Who is eligible (decided by the App)

A principal may confirm in its window only when **all** hold, checked at the moment of the window OK:

- kind `device` with a registry record (never the legacy shared token, the chat bridge's or the gate worker's reserved ids, or the standalone container's token: decided by the authenticated principal, never by a client label); local pinned and Link pairings both qualify;
- `ownComputer.userId` set, and a fresh read of `config/auth/list` shows that user as the active, non-system **owner** (an ownership change ends it; a failed read means no window OK; for a Link device, `cloudUserId` must be that same user);
- `credentialStore` is a desktop store (`keychain`, `credential_manager`, `secret_service`), recorded at pairing from the pairing CLI's report; never `file` (`--credential-store=file`, `setup --service`, no desktop keyring);
- `windowConfirm` is `true`.

The store and the platform are the pairing CLI's own report. The App can't check them; the root of trust is a pairing the owner authorized. A record from before 0.32 has no `credentialStore` and no `ownComputer`, so it is never eligible: its window and the page say "Pair this computer again once to confirm here" (D2).

### 2. Registry and pairing (Relay)

- `DeviceRecord` gains three optional fields: `credentialStore?: "keychain" | "credential_manager" | "secret_service" | "file"`, `ownComputer?: {userId, atMs}`, `windowConfirm?: boolean`. `validateDevice` checks them by type and value (unknown values: registry corrupt, as for other fields).
- Pairing metadata (v1 and v2) takes `credential_store` (one of the four values; missing = unknown, never eligible).
- `POST /pair/v2/arm` and `/pair/v2/arm/link` take `own_computer: boolean`. The arm is the owner's own authenticated ingress session (`checkOwner`, `pair-v2.ts:52–59`), so this is the owner's statement; the App stores the owner's user id with the pending pairing and writes `ownComputer` and `windowConfirm: true` at activation only when the stored store value is a desktop store. v1 code pairing never sets `ownComputer`.
- **Re-pairing keeps the phone.** A new pairing is a new device; the previous device of the same install is revoked as today (`cli/pairing_previous_device.go`). When the arm was the owner's, the App copies the revoked predecessor's `confirmPhone` to the new device in the same registry write, so the person doesn't link their phone again and no link ask precedes the first risky change. A code pairing copies nothing.
- Revoking a device ends everything.

### 3. The NOVA page (Relay)

- Each computer row: "Confirm in its window: On / Off", or why not ("someone else's computer", "key kept in a file", "paired before 0.32: pair it again once").
- **Owner only** (fresh `checkOwner`, CSRF-guarded POST, logged with the user id): "This is my computer" (sets `ownComputer` to the clicking owner and, with a desktop store, turns the switch on: one click) / "Not my computer" (clears both), and the On/Off switch. Administrators see the state, can revoke the device as today, and can't turn it on.
- The warning text above, verbatim, under the switch.
- "Recent window confirmations": the last 50, kept in `/data/gate/window-log.json` (time, computer, title), written with a rename; a write that fails is logged and doesn't block the OK.
- Texts come from `cli/confirm_strings.*.json` through the worker's `/texts` route, as the approval view's do.

### 4. The ask contract (Relay and CLI)

- `GET /health` adds `window: 1` on an App that has this contract. New `GET /gate/v1/me` (device principals) answers `{window: true|false, why}` with §1 checked now, so the CLI can word `say` and `next_step` at plan time.
- `POST /gate/v1/ask` (open) takes an optional `presence: "present" | "away" | "unknown"` (sent only to an App with `window: 1`) and answers `channels` with `"window"` added when §1 holds at open time. The CLI shows [Confirm] only then.
- New `{ask_id, op: "window"}` on the same route. The App re-checks §1 (fresh owner read), then, in the same synchronous state change that phone, page, cancel, and expiry use (`settle` in `gate-asks.ts`; the first terminal state wins), marks the ask approved through the window and answers `approved {grant_id, until}`. Another principal's or an unknown id: `404 GATE_ASK_UNKNOWN`. An ask already ended: its terminal state, never a second grant. §1 not met: `409 GATE_WINDOW_OFF`; a failed owner read: `503 GATE_UNAVAILABLE`. In both, nothing is approved and the ask stays open for the phone and the page.
- New `{ask_id, op: "away"}`: the CLI reports that the person left (20 seconds without input, or the screen locked) while the window waits.
- A link ask (`/gate/v1/phone`) can't be approved through the window.
- New `{op: "window_off"}` (device principals only) sets the caller's own `windowConfirm` to `false`. No device route turns it on.
- **When the phone asks, with a window offered:** at once on `presence: "away"` or a later `op: "away"`; after 20 seconds on `"unknown"` (Linux, where HA NOVA has no idle reading); after 60 seconds on `"present"`. The ask keeps its absolute 3-minute deadline; the phone waits for what is left. The page shows the ask at once. A delay never removes a channel, and a failed window still leaves the phone and the page. Presence comes from the computer and is not trusted for anything else: a lying client can only delay its own owner's phone.
- **After-note:** (1) the App settles the ask synchronously with its winning outcome, so nothing else can win after; (2) for a window winner with a linked phone, it calls `POST /phone/end {ask_ref, outcome: "window", link, lang, title, computer: {id, name}}` on the authenticated worker and waits for its answer, at most 3 seconds; (3) only then it hangs up the `/phone` request (which now carries the same 64-lowercase-hex `ask_ref`). The same end route covers a phone that was never asked; there is no separate `/notice`. The worker keeps at most 1,024 four-minute lifecycle entries. An end before registration prevents the question; an end during a send is retained until the phone call unwinds; a late tap cannot replace the App's winning outcome; a duplicate end is a no-op. A normal result already in flight is followed by the window correction. Question cleanup uses the question's random tag, never the stable note's tag. The note uses `ha-nova-window-<hash of computer id>`, so renaming a computer does not stack notes. Its catalog keys are `phone.window.*`, with names through `sayText`; it states the computer and action, without a cosmetic daily counter or time-zone state. iOS uses passive delivery; Android uses the low-importance `HA NOVA confirmations` channel. The worker serializes delivery per computer and suppresses an older pending stable note once a later end is recorded. The App must submit ends in winning order per computer; its three-second recording budget must include any queue wait. Other outcomes keep the existing withdrawal/result path. A failed or late end: the App hangs up anyway, the worker withdraws as today, and the failure is logged. The App appends to the window log either way. Best effort: no delivery failure undoes the OK, and an iOS clear can fail, leaving the old buttonless question note alongside the stable note. With no phone linked, only the log shows it.
- **Pause and limits:** a window approval counts as a person's answer and resets the unanswered count, like a page approval. An ask counts as unanswered on the phone only if its phone ask was actually sent and stayed out at least 15 seconds (today: 15 seconds of ask-open time, `nova/src/http/gate-owners.ts:80–89`). The hourly limit protects the phone, not the window: past 10 asks in an hour, a computer's next ask opens **without the phone** (window and page only), as during a pause; a hard cap of 60 asks an hour per computer (`429 GATE_ASK_LIMIT`) protects the App.
- Wire values are closed sets: `window` in `channels`, `presence`, `GATE_WINDOW_OFF`, and the ops ship in the same App release as the CLI that sends them.

### 5. macOS: keep the key where only the new `ha-nova` reads it (CLI and release)

Needed for the macOS statement; Windows and Linux gain nothing from it, since every same-user process reads their key.

1. **New signing identifier.** `SIGNING_IDENTIFIER` in `scripts/release/build-sign-darwin-binaries.sh` and the check in `verify-macos-signature.sh` change from `com.markusleben.ha-nova.cli` to `com.markusleben.ha-nova.cli2` (same Developer ID team). New Keychain items trust only binaries with the new identifier, so no earlier release reads them silently, even with `HA_NOVA_KEYRING_SERVICE` (`cli/keyring_service.go:36–40`).
2. **New slots.** The new binary can't read items the old identity created without a Keychain prompt, and today's setter modifies an existing item in place, which keeps its old ACL (`cli/cloud_oauth_secret_darwin_api.go:157–202`). So 0.32 writes to new slots under a root no legacy slot can have: `com.markusleben.ha-nova.cli2/<kind>/<profile>`, kinds `device`, `device-pending`, `relay-token`, `link-current`, `link-pending`, `link-retiring`, the profile name percent-encoded (legacy slots all start with `ha-nova`, `cli/device_credential_store.go:47–58`, `cli/cloud_oauth_secret_store.go:14–18`; a suffix such as `.v2` would collide with today's slot for a profile named `v2`). It refuses to write into a slot that already exists unless it is its own verified earlier write, so new items are created fresh and trust only the new identity.
3. **One re-pair after the macOS update, about one minute.** The shipped updater replaces the bundle before running any new-binary code, so 0.32 does not promise a pre-switch migration or rollback on a declined sign-in. No bootstrap, fallback runtime, or bridge release is needed.
   - The new binary never opens a Keychain dialog for an old item: any legacy lookup disables authentication UI. Missing or unreadable credentials mean "not paired under 0.32", not a generic error or repeated prompt. A no-UI read must not silently make an old device key window-eligible.
   - The first command that needs this Mac's pairing returns a distinct needs-re-pair result with one next step: one Home Assistant sign-in, about one minute. That same flow asks whether this is the person's own computer, writes the new key directly into its new slot, and carries the phone link over (§2). There is no second pairing step for the window OK. Link sign-in state uses the disjoint generation slots too; missing or unreadable legacy state must lead into this recovery flow without a Keychain prompt; already-created new-slot pending/retiring generations stay intact.
   - Activation revokes the predecessor's device credential on the Relay. Its leftover old Keychain item then works nowhere, including through an older signed binary. Delete an old item only when that succeeds without prompting; revocation, not deletion, closes the old export path. Preserve interrupted new-slot and Link-generation recovery under the existing locks.
   - Before an agent starts the update, `check-update` and the update skill must explain that this Mac needs the person once to re-pair, so the agent asks first. The already-shipped CLI cannot acquire new preflight code: put "On macOS, 0.32 asks you to pair this computer again once." first under the release's action-needed heading, which its existing release digest exposes. Test that path with the old CLI, not only the new implementation. After updating, the agent gets the needs-re-pair status and the same single next step.
4. **No copy to a file on macOS.** `migrateKeyringDeviceCredentialToFile` (`cli/device_credential_migration.go:51–100`) refuses on macOS when a Keychain key exists: `pair --credential-store=file` and `setup --service` pair again instead, and the new device reports `file`. **Windows and Linux:** the same commands keep copying the key into a file (no new pairing, so no break), but first send `window_off` for every profile they copy; if that fails, nothing is copied and the command says why. This guards the honest path only: there any same-user process can read the key anyway.
5. **The key goes only to its own Relay.** At pairing, the secure URL and SPKI pin are stored in the same Keychain item as the key; `relayFunctionalTransport` (`cli/relay_transport.go:127–133`) uses the item's URL and pin on macOS and ignores `config.json`'s copies (doctor reports a mismatch). Editing `config.json` redirects nothing.
6. **`HA_NOVA_KEYRING_SERVICE`** is ignored in release builds (tests keep it through a build tag).
7. **Inventory test.** A test lists every caller that reads the device key or the relay token and fails on a new one; each listed caller sends it only through the pinned transport.

Honest limit kept: a person who allows a Keychain prompt for a program that isn't HA NOVA hands that program the key.

### 6. The window, the wording, and the agent (CLI and skills)

- **One dialog everywhere.** The window shows the stored plan's own title and full prompt, built locally from `cli/confirm_strings.*.json` as a window plan's is today; the phone shows its short summary and the page the worker's items, from the same strings. macOS NSAlert, Windows `MessageBoxTimeoutW`, Linux zenity, unchanged (`docs/work/2026-11-10-wider-confirm-window-spec.md`).
- **With `window` in `channels`:** [Confirm] [Cancel]; footer "Your phone asks too if nobody answers here." (without a phone: "Or confirm on the NOVA page."). Confirm sends `op: "window"` and, with the grant, goes on as after a phone OK (the 0.31 recheck, then the sends). Cancel sends `op: "cancel"`. A phone or page answer closes the window. On `503`, Confirm retries quietly for up to 5 seconds; then, as on `409`, the window says "This computer can't confirm right now: confirm on your phone or on the NOVA page" and keeps waiting (the phone is asked at once).
- **A relay plan too long for the window** is never refused for that (today `windowTooLong` runs only for window plans, `cli/confirm_window.go`): the window shows the first items, "and N more: the full list is on the NOVA page", and no Confirm, since Confirm only approves what the window showed; the phone is asked at once.
- **Without `window`:** today's waiting window (`gate.window`, [Open in Home Assistant], [Cancel]) plus the one-line reason from `/gate/v1/me`.
- **Presence:** while the window waits, the CLI reads the idle time every 5 seconds (macOS `ioreg -c IOHIDSystem` `HIDIdleTime`; Windows `GetLastInputInfo`; Linux `unknown`), sends it with the open, and sends `op: "away"` once it passes 20 seconds. No new dependency, no cgo.
- **The agent says what the person sees.** With `window: true` from `/gate/v1/me`, `say` uses `say.window_ask` ("Confirm in the window on this computer. Not at the computer? Your phone asks shortly, or use the NOVA page."), `next_step` and `channelAsks` (`cli/confirm_code.go:108`, `cli/plan_store.go:197–209`) name the window, and the waiting answer of `ha-nova mcp` uses `say.window_waiting` (`cli/mcp_stdio_apply.go:128`). Without it, today's texts.
- **No second ask for the same plan when the command's wait ends.** Today `ha-nova apply` cancels the App's ask when its own 90 seconds run out (`cliWindowWait`, `cli/gate_client.go`), so a later tap hits a dead ask and the next apply asks again. 0.32 leaves the ask open, keeps its id with the stored plan, and answers `waiting_for_approval`; the next `apply --plan <id>` joins the same ask (as `ha-nova mcp`'s job already does, `cli/mcp_stdio_apply.go:103–135`) and uses a grant that arrived meanwhile within its 2 minutes.
- No flag, environment variable, or tool argument confirms; the window's answer comes only from the window process's output, as today.
- **Setup:** the box from "What a user sees" 1 on the "safety net" screen (browser and terminal flow), only on sign-in pairing; the CLI sends `own_computer` with the arm and `credential_store` with the pairing.
- **`ha-nova setup confirm-window off`** also sends `window_off`; `on` turns the local setting back on and opens this computer's row on the NOVA page, where the owner turns the App's switch on.
- **Dashboard delete onto the App's ask** (computers only). A dashboard delete is one request the gate rates typed (`cli/gate_verdict_test.go:84`), so its plan takes channel `relay` and asks once, instead of this computer's window plus the App's second ask. Rooms plans (preview-level: the chat "yes") and raw items typed only by a skill's mark keep this computer's own ask (`gateChannel`).
- **Skills sweep** (behavior-changing, so an end-to-end agent run on the test bed): the confirmation wording becomes "your own confirmation: the window on your computer, your phone, or the NOVA page; a code only where `say` shows one" in `skills/ha-nova/SKILL.md:99`, `skills/write/SKILL.md:78`, `skills/maintenance/SKILL.md:50–55,95`, `skills/admin/SKILL.md:44–46`, `skills/updates/apps.md:29–31`, `skills/yaml-config/SKILL.md:37`, `skills/assist/SKILL.md:86`, `skills/ha-nova/batch-safety.md:67`, `skills/ha-nova/capability-answer.md:92`; `skills/dashboard/SKILL.md:60` passes `--confirm` only when the plan carries a code. The agent never asks in the chat on top of the window. Word budgets stay ratchets: trim, never raise.

### 7. What is not in 0.32

- Chat apps: no change to their asks, levels, codes, or the read-only switch, on the App and on the standalone container. Moving chat asks onto the NOVA page, or a read-only wait tool, would change a working connector flow; both are later changes.
- One phone per person: existing links stay exactly as they are; the only new step is the carry-over on re-pairing (§2).
- Touch ID / Windows Hello per OK.

### Asks that stay above the targets, and why

1. **S7 (no phone in a chat app): two asks, and Claude asks again each time the AI checks back while a change waits.** The AI can read a chat code, so Claude's own "Needs approval" prompt on "Run a confirmed change" is the only human check (`docs/reference/chat-apps.md:42`). Way out: link a phone, then "Always allow" everything (S6). Moving chat asks onto the NOVA page or adding a read-only wait tool would change the connectors' tools and flow, which 0.32 keeps unchanged (acceptance criterion).
2. **Dead ends in the chat:** below Manage everything without a phone, and the standalone container without a linked phone, refuse risky changes. No channel a person controls exists there; the refusal says how to link a phone.

### MAR-209: a service-call listener makes every action risky

On Markus's home a light call is risky: `automation.rolladen_watchdog_dynamische_cover_gruppen` triggers on every `call_service` event (no domain filter), and its script `script.rolladen_watchdog_check_group` calls `cover.open_cover`, `close_cover`, and `set_cover_position` with templated targets. The CLI can't tell which covers, and a cover may be a garage door or gate, so any call that can start the watchdog is rated risky (reasons `CALL_SERVICE_LISTENER_UNEXPLAINED`, `RUN_EVENT_LISTENER_UNEXPLAINED`, `UNRESOLVED_TARGET`). That is correct and fail-closed today, and it makes every action in that home ask.

Approved fix (D6, Markus, 2026-11-16): **rate an unresolved target by every entity it could pick.** For a call whose target the CLI can't resolve (a template), it lists every entity that call's domain could address in this home, from the live state list (which also has YAML entities without a unique id, not only the registry), and rates each one as if the call named it, with the existing rules unchanged: unknown, custom, or missing cover classes count as doors; template and command platforms, groups, `switch_as_x`, scripts (an unresolved `script.turn_on` walks every script), and device siblings are followed as today (`cli/tier_engine.go:300–345`, `cli/tier_walk.go:109–117`, `cli/tier_rules.go:203–225`). Only when every candidate rates below risky and every read succeeded does the unresolved target stop making the call risky; any unknown candidate, failed read, or `calls.unknown` keeps it risky, and every other risky reason stays. It applies only to calls in the same run that follows the plan's own call, with no `delay`, `wait_template`, `wait_for_trigger`, or step that creates or reloads entities before them. A config save (an automation or script stored to run later, drafts included, `cli/plan_config.go:425–449`) and every later or delayed call keep today's rating, because entities added later would never be checked. The change lands in the shared classifier, so the App's check follows; negative fixtures (a template cover classed blind whose action unlocks, an unresolved script target that reaches an unlock, a YAML cover without class, a delayed call, a save) pin it in both the CLI's tests and `gateVerdict`'s, since parity alone could repeat the same wrong answer twice. `RUN_EVENT_LISTENER_UNEXPLAINED` gets the same bound only if the bed copy of the watchdog shows it comes from the same calls. Stated honestly: "no risky effect in the model HA NOVA checks"; physical wiring HA NOVA can't see (a light relay that is really an opener) stays outside it, as today.

If Markus's home does have an access cover the watchdog can pick, the bound doesn't clear it, and S1 there costs one window click per light (no phone buzz while he's at the computer). The next option (D7, not built unless needed): the owner acknowledges a specific automation or script version on the NOVA page ("this never opens <garage door>"), pinned to its config hash and dropped on any edit; it lowers only that automation's unresolved cover targets, never a lock, the alarm, or an access entity it names. It rests on a person's promise about a template, so it is weaker. Markus checks which case his home is with one read-only `ha-nova plan call light.turn_on` on the 0.32 RC (it reads and sends nothing; agents never run it on his home).
