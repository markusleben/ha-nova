# Human confirmation channels: the confirmation window (part 1) and the phone (part 2) (2026-10-17)

Status: active

Inputs: `docs/internal/2026-10-17-human-confirmation-channels.md` (matrix, hands-on results), `docs/work/2026-10-17-confirmation-hardening-spec.md` (#716: plan secret, channel binding, fallback E), `docs/work/2026-10-16-mcp-human-confirmation-spec.md` (form C).

Goal: a typed-tier `apply` (unlock, open a gate or garage, disarm, delete, reload) asks the human through the simplest channel the model can't forge, chosen automatically. Threat model and actors T1–T3 as in the hardening spec §1: this change closes T1/T2 paths where a window can open; T3 stays stated, not solved.

## 1. Channels and order

A typed plan's channel is set when the plan is made and is part of its code's MAC (`confirm_code.go`), so editing it in the plan file breaks the plan.

| Order | Channel | When | The human |
|---|---|---|---|
| 1 | A `window` | this computer can show a window (§2) and the user has not turned it off (§4) — in the CLI and inside `ha-nova mcp` alike | clicks Confirm in a native window |
| 2 | B `phone` | no window can open (or windows are off) and a phone is linked on this computer (§7.2): one Companion-app phone, chosen by the user, whose Home Assistant user is an administrator other than the Relay's | taps the action's button (e.g. “Unlock”) in a notification on the linked phone or its Apple Watch (no device unlock: whoever holds the phone can answer the one open request) |
| 3 | C `form` | otherwise, when the plan is made inside `ha-nova mcp` for a client that declares form elicitation (not `--no-forms`): remote, headless, and later phone connectors | types the four-digit code shown in the form |
| 4 | E `chat` | everything else | types the code shown in chat; `say` says the assistant sees it too |

- Why the window comes first (decision 2026-10-17, coordinator, logged in `docs/choices.md`): a model with a shell can start `ha-nova mcp` itself, declare forms, and answer its own form (the code is in the form's message); it cannot answer an OS window without computer use or accessibility rights. The approved order was C before A; it was flipped in this PR before merge.
- A window that can't open falls back to the linked phone (§7), else to the form in a forms session, else to chat.
- Since 0.27 (`docs/work/2026-10-18-onboarding-0.27-spec.md` §7.4, `cli/confirm_both.go`): where a window can open and a reachable phone is linked, both ask at once and the first answer counts; a window that can't open then leaves it to the phone in the same apply.
- A window plan is never confirmed in a form (`formPlan` skips it): applied inside `ha-nova mcp`, it opens its window too.
- A form or window plan never takes a code from argv: `apply --confirm` is ignored for it (`CONFIRM_IN_WINDOW`, `CONFIRM_IN_FORM`; no attempt is used). Its code never leaves the process: not in the envelope, `say`, the plan file, or the apply result.
- MCP without forms (Claude Desktop, `--no-forms`, a client that declares no elicitation) now detects like the CLI, so leaving out the capability or adding `--no-forms` no longer yields a code the model sees where a window can open.

## 2. Detection (CLI only; no flag, no environment variable picks a channel)

| OS | Available when | Window |
|---|---|---|
| macOS | `/bin/launchctl managername` prints `Aqua` (a logged-in desktop session; SSH and background sessions are not) | `/usr/bin/osascript` `display dialog`, by absolute path, with an empty environment; buttons Cancel (default, so Return cancels) and Confirm; message and wait passed as arguments, never as script source |
| Windows | the process is not in session 0 (SSH, services) and its desktop is `Default` (Codex's sandbox uses a private desktop no one sees) | `MessageBoxTimeoutW` in process (no program path, no environment): OK/Cancel, Cancel the default, topmost |
| Linux | `DISPLAY` or `WAYLAND_DISPLAY` is set and `/usr/bin/zenity` exists | zenity by absolute path (never PATH: a fake could "confirm"), with an allowlisted environment (no `LD_PRELOAD`, `GTK_MODULES`); Cancel the default. kdialog is not used: its continue/cancel mode makes Continue the default, so a KDE desktop without zenity uses chat |

Linux reads two environment variables because a dialog cannot reach a display without them; unsetting them only moves a plan to E (§5, T3).

## 3. Apply with a window plan

1. Before the claim, apply re-plans the stored request (as apply does) and opens the window only when the fresh hash, tier, and id match the plan and at least 15 s remain before expiry (less: `PLAN_EXPIRED`, plan again). The window shows that fresh text (`confirmText`: the plan's code-free prompt, a delete's copy note, "Requested by your AI assistant. Go ahead only if you want this."), never the plan file's own `prompt`.
2. After a second in the open window, stderr says "A confirmation window opened on this computer — confirm there." (hosts that show a running command's output show it).
3. Answers:
   - **Confirm:** the CLI derives the plan's code in process (`humanAnswer`), and apply then claims, re-plans, and checks as always: a change while the window was open is drift (exit 2, nothing sent, a new plan).
   - **Cancel:** `CONFIRM_DECLINED`, exit 4, nothing sent, the plan stays.
   - **No answer** (timeout, closed, killed): `CONFIRM_CANCELLED`, exit 4, nothing sent, the plan stays; applying again opens the window again. Its `next` also names the way out when no window appeared: Home Assistant itself, or `ha-nova setup confirm-window off`.
   - **Could not open:** fallback E, never silent: apply claims the window plan (so one window plan yields at most one chat plan), saves a new chat plan (same hash, a fresh code) in its place, and returns exit 3, `say` starting "The confirmation window couldn't open on this computer." and ending with #716's note, and a `next_step` naming the new plan.
   "Could not open" is only a window that provably never showed: macOS — osascript could not start, the script never logged that it reached the window (it did not compile: a sandbox, -2740), or `display dialog` refused at once (-1713); Windows — `MessageBoxTimeoutW` returned 0; Linux — zenity could not start or reported that it could not open or connect to the display. A window that showed and then ended is no answer, never a fallback, so killing it can't force E.
   - **The CLI is stopped** (SIGTERM, SIGINT, SIGHUP not ignored since start): the window closes first, nothing is sent, a linked phone's ask is told "Stopped on the computer", then the process ends by that signal. A SIGKILLed CLI: on Linux zenity dies with it (Pdeathsig); macOS's dialog stays until its own timeout (known limit); Windows' box lives in the process.
4. Timeout: 90 s from the CLI (a late Confirm still re-plans, sends, and verifies under Claude Code's 120 s default command timeout; Claude Code then backgrounds the command, it does not kill it), 40 s inside `ha-nova mcp` (under the common 60 s tool-call timeout); never past the plan's expiry. `next_step` tells the agent to give the command up to 2 minutes. The CLI times itself out (Codex does not kill a unified-exec process on Esc).
5. The answer comes only from the window's own child pipe (macOS, Linux) or call (Windows): never stdin (Codex `write_stdin` can type into a process), argv, or a file.

**Code in the window? No.** A process that can click the window (macOS with Accessibility or input-posting permission, Windows UI Automation, X11) can also read a code shown in it and type it, so a typed code adds a step for the human and no protection; buttons with Cancel as the default stop a stray Return.

## 4. Turning windows off

`ha-nova setup confirm-window off` writes `"confirm_window": "off"` at the top level of `config.json`; typed plans then use the form where the MCP client shows one, else E. Turning off is confirmed in the window itself, so a model that runs the command can't complete it; where no window can open, nothing is written (E applies anyway, and an "off" written there would persist into later desktop sessions). `on` (the default) removes the key and needs no confirmation. If a window opens where no one sees it, the human sets the key by hand (the command prints the path after a window that got no answer). Editing `config.json` is a T3 action, as is every other config edit.

## 5. Honest limits

- **Same-user clicks:** on Windows and X11 any same-user process can click the window (a plain `BM_CLICK` message, `xdotool`): there A stops T1 slips and documented-command T2 paths, not a model that automates the desktop. macOS needs Accessibility or input-posting permission for that; a terminal granted Accessibility (window managers) makes it clickable. Wayland blocks global input injection, but zenity is a child of the model's shell: tracing it (Yama scope 1 allows own descendants) or a GTK module named in the user's GTK settings file can still forge Confirm (T3).
- **Computer use:** with a host's computer-use feature on, the model can click the window on every OS.
- **Sandboxes:** inside Codex's seatbelt or Claude Code's sandbox the window fails to open (verified with an approximated Claude Code profile here); apply then falls back to E and says so. In practice `ha-nova` already runs outside Codex's sandbox because it needs the network.
- **Forced fallback (T3):** a model that wraps `ha-nova` in its own OS sandbox or a process limit (`ulimit -u`, so the window program can't start), unsets `DISPLAY`/`WAYLAND_DISPLAY`, runs it from an SSH session, or points Linux `DISPLAY` at a virtual display it controls gets E or a window it can click. Each is the same class as reading the Relay credential (hardening spec §1.1), which defeats every channel on this computer.
- **Form C is not human-only in a host that also gives the model a shell:** the model can start `ha-nova mcp` itself, declare forms, and answer its own form (the code is in the form's message). With the window first this is closed where a window can open; it stays where none can (headless or SSH hosts with a shell, a sandboxed command, the windows turned off).
- **Unattended screen:** a `tmux`/`screen` session started on the Mac's desktop and reattached over SSH still reports `Aqua`, so the window opens on the Mac's screen, where whoever is there can click it; the remote user sees no window and gets no answer.
- **What the window shows:** a summary (names, the action, the reasons), not a config diff or the server name; with several homes the window does not say which one.
- **A window no one sees** (a virtual display, behind a full-screen app) times out every time, the off switch included; the way out is editing `config.json` by hand (§4) or Home Assistant itself.
- **MCP:** the server answers no `ping` while a window is open (up to 40 s); a client that gives up on the tool call earlier never sees a confirmed result.
- **Untested:** Windows and Linux windows (no machines here; code paths kept minimal), Claude Desktop and other MCP hosts showing the window, a locked screen or full-screen app hiding it (the timeout then says "no answer").
- **Language:** the window text is English, like the forms.

## 7. Part 2: the phone (B)

Inputs: the channels report §2 B and §3 B (sniff and forge paths reproduced on a throwaway HA).

### 7.1 Order: window → phone → form → chat (decision 2026-10-17, logged in `docs/choices.md`)

The phone comes before the form: a model with a shell can start `ha-nova mcp` itself, declare forms, and answer its own form (the code is in the form's message); it can't tap a phone. It comes after the window because the window needs no phone, no push round trip, and no Companion app, and is equally out of a same-user model's reach on macOS. A window that can't open moves the plan to the phone where one is found (`windowFallback`), else to the form or chat as before. Since 0.27 a reachable linked phone asks together with the window (0.27 spec §7.4), so `windowFallback` reaches the phone only when it was not found before the window opened.

### 7.2 Who confirms, and where (revised 2026-10-17: the linked phone)

#719 sent the push to every Companion phone on the owner's `person`. In a family home that is wrong twice: shared or family devices on the owner's person got confirmations, and the person using HA NOVA may not be the owner (a partner owns the instance). Now:

- **One linked phone per computer and Home Assistant.** The user links it once (§7.9). `config.json` stores, at the top level, `"confirm_phone": {"<owner user id>": {"service", "device_id", "user_id", "name"}}`: the notify service, the device registry id, the Home Assistant user the link tap arrived as (`context.user_id`), and the phone's name. It is keyed by the owner's user id because that is unique per Home Assistant (a removed or renamed server profile can't carry it to another home); each computer has its own `config.json`, so each computer links its own person's phone.
- **Only the linked phone gets anything.** Confirmations, setting changes, and the link question go to that one notify service; no other phone is ever sent a notification (hard rule, pinned by tests). Before each send the CLI re-resolves the service from the stored device id; a phone whose service is missing, or whose name another Companion device shares (both would get the push), is unreachable — refused, never sent.
- **Who counts:** a tap counts only from the stored user, and only while that user is an active, non-system Home Assistant administrator (owner or `system-admin` group: confirming unlocks and deletes) other than the Relay's own user.
- **Unavailable** when the Relay acts as the owner (a standalone Relay on the owner's long-lived token; the identity check can't hold there), and on a computer with no linked phone (the next channel applies).
- **Reads** (a fixed allowlist, `checkPhoneRead`, not the model-facing raw allowlist): `auth/current_user`, `config/auth/list`, `config/device_registry/list` (every `mobile_app` device's name, also one whose entities are disabled or removed), one fixed `POST /api/template` with the linked device id and those names as its only variables (never template source), and `/api/services`. The template lists every `person` with a user and its `mobile_app` device trackers (device id, name, slugged notify service: Home Assistant's own `slugify`, so "Markus’s iPhone" matches), the service of every named device (to detect shared names), and the linked device by id.

### 7.3 The notification

`notify.mobile_app_<slug>` of the linked phone with the plan's goal as the title ("Unlock “Front Door”?", at most 80 characters) and a short body: the first reason it needs a confirmation that the title doesn't already say ("This also unlocks “Entrance Door” through the automation “Guest”."), then "Requested by “<computer>”." and how to show the buttons on that phone (the device registry's manufacturer: "Apple" is iOS, any other is Android): "Press and hold to answer." on iOS, "Pull down to answer." on Android (there first: a collapsed Android notification shows one line of text), both when unknown (a plain tap only opens the app; on Android a long-press opens settings; "Can't be undone." first for a delete without a copy). The computer and the chat say the same per platform ("Press and hold the notification, then tap “Unlock”." / "Pull the notification down, or tap its arrow, then tap “Unlock”."). The full text and "only if you started this" stay in the terminal. `data`: `tag: ha-nova-<plan id>-<8 random hex>` (fresh per attempt, so a late result of an earlier attempt can't replace it), actions named by the goal's verb ("Unlock"; "Confirm" for a longer verb) (`destructive`; no `authenticationRequired`: an Apple Watch never fires such an action, and the watch must be able to confirm, so whoever holds the linked phone can answer the one open request, for at most the 90 s wait; Link, Move, and Stop keep `authenticationRequired`: they last beyond one request and are asked at the computer; `true` on iOS and an unknown phone, the string `"true"` on Android (a phone linked as an iPhone keeps the bool even if its maker changes later), whose push relay copies it into FCM data, which takes strings only — a bool fails the whole push, and Home Assistant only logs that) and Cancel, iOS `push.interruption-level: time-sensitive` (a pending action; linking, moving, and stopping are `active`: asked while the person is at the computer) and `apns_headers.apns-expiration` (the wait's end), Android `priority: high`, `channel: HA NOVA`, `importance: high`, `timeout` (seconds left), `ttl` (milliseconds left: FCM drops an ask it couldn't deliver in time; the relay drops a `ttl` of 0). When the ask ends, a result notification replaces it (same tag, no buttons, no ids, `active`, Android `timeout` 10 minutes): "Done: Unlock “Front Door”" (apply's outcome: Done only when verified; else Sent, Check, Didn't work, Unclear, or Not done), "Cancelled: …", or "Not confirmed: … No answer reached Home Assistant. Nothing changed." — so a tap that never arrived (seen with a watch app holding stale state) is never silent. Linking ends with "Linked to HA NOVA" or "Not linked"; moving and stopping with "Approved" on the old phone (the computer shows the final result).

The action ids are `HANOVA_OK_<32 hex>` / `HANOVA_NO_<32 hex>`, drawn per apply from `crypto/rand`, held only in the apply process: never printed, logged, stored in the plan file, or in the envelope.

### 7.4 Waiting and the identity check

- The CLI listens through the Relay's existing bounded `collect_events` (`subscribe_events` `mobile_app_notification_action`, `max_events: 1`, 10 s cap) in two overlapping lanes 5 s apart, so one re-subscribes while the other listens. No Relay change (no App release, works with installed Relays). First a 1 ms probe window must succeed (the Relay starts a window only after Home Assistant acknowledged the subscription), so a Relay that can't subscribe gets no notification at all; the push then goes out 1 s after the first lane starts. The phones are sent to in parallel, bounded by the wait, so a stalled notify service never holds apply past the deadline.
- An event decides only if `data.action` is one of our two ids. It then counts only if `origin` is `REMOTE`, `context.user_id` is the linked user, and that id is not the Relay's own user; otherwise the wait ends as `CONFIRM_REJECTED` (exit 4, nothing sent; worded as "the tap came from a device signed in to Home Assistant as someone other than the person whose phone is linked"). After the answer (or none) a result notification replaces the ask (§7.3), after apply's output, for at most 10 s (2 s inside `ha-nova mcp`, whose server keeps sending). Ending, not ignoring: a matching id from someone else means the id leaked, and the human can simply apply again for a fresh one. Other actions (other notifications' buttons) are ignored.
- Timeouts as the window: 90 s in the CLI, 40 s in `ha-nova mcp`, counted from before discovery, never past the plan's expiry, at least 15 s left or `PLAN_EXPIRED`.
- Outcomes: Confirm → the link is read again (still the same phone and user, still an administrator; else `CONFIRM_UNAVAILABLE`, nothing sent), then the code is derived in process (`humanAnswer`) and apply claims, re-plans, and checks as always; Cancel → `CONFIRM_DECLINED`; no answer → `CONFIRM_CANCELLED` (apply again sends a new notification); could not listen or send → `CONFIRM_UNAVAILABLE`. All keep the plan and send nothing. A phone plan never falls back to another channel. A code from argv never replaces the phone (`CONFIRM_ON_PHONE` when apply is reached without the answer).

### 7.5 No downgrade: the link is the pin

The link replaces #719's automatic pin. Once a phone is linked, a typed plan whose phone can't be used now is refused (`CONFIRM_UNAVAILABLE`, exit 4), never moved to the form or chat; its `next` points to `ha-nova setup confirm-phone list`, which names the reason with one line each: the device was removed, its notify service is gone (app signed out), another device has its name, its user is no longer an administrator, the Relay now signs in as that user or as the owner, or a read failed. When the owner can't be read and any link exists in `config.json`, or `config.json` can't be read at that moment, the plan is refused as well. A typed plan's apply re-plans on its stored (sealed) channel; the link is re-read once right after the tap (§7.4), and a setting change or a link tap counts the same way only while its phone and user are still current. A computer with no link never reads phones and uses the next channel. Editing `config.json` is T3, as for the window.

**Migration from #719** (in `main` only, never released): a `"confirm_phone": {"<owner id>": "on"}` pin from #719 refuses typed plans where no window opens (`CONFIRM_UNAVAILABLE`, "choose your phone once") until a phone is linked; it never downgrades. #719's `"off"` reads as no link. Linking from the old pin counts as "no linked phone yet" (§7.9); `off` from the old pin is refused ("link your phone first").

### 7.6 Forgery paths closed (raw guard, `cli/relay_raw_guard.go`)

Already refused before this change: `fire_event`, `POST /api/events/*`, `/api/webhook/*` (any method), WS `webhook/*` (`webhook/list`, `webhook/handle`), `subscribe_events` without a type, `*`, or `call_service` (the notify call carries the ids). Added: `subscribe_events` and `subscribe_trigger` on `mobile_app_notification_*` and iOS `ios.notification_action_fired` (Android echoes every action id and its webhook id in them), and any raw `subscribe_trigger` holding a template (an event trigger's type can be templated). WS `cloud/status` (lists cloudhook webhook ids) and `mobile_app/*` (the local push channel) are not on #718's raw WS allowlist, so they stay refused (pinned by tests). The CLI's own discovery reads and its listener never go through the raw routes: they use their own fixed allowlist (`checkPhoneRead`) and a fixed subscription body, so nothing here widens what a model can send raw. Phone plans carry #718's plan seal like every typed plan; an edited phone plan is never asked on the phone.

### 7.7 Honest limits

- **T3 as before:** a model that reads the Relay credential or edits `config.json` (pin off, window off) is not stopped.
- **Leaked ids are not enough on their own:** a forged tap also needs the linked user's identity. Paths that carry it: an Android (unencrypted) registration's webhook id plus `POST /api/webhook/<id>` from outside the Relay. The raw guard closes the known ways to learn it through the Relay (the registry's `unique_id` only since the linked-phone change, §7.9); a model that builds its own reader (for example a SQL sensor over the recorder's event table through a config flow) or reads HA's debug log after raising its level (`logger.set_level` is preview) could learn ids — T3-adjacent, stated. iOS registrations are encrypted: `webhook/handle` and a plain webhook post are refused there.
- **Notification overlay (closed):** an automation that watches `call_service` or a phone notification event other than the tap could copy our buttons into a notification with its own text; the linked user's genuine tap would then confirm text they never read. Writing such an automation or script (event trigger or `wait_for_trigger` on `call_service`, `mobile_app_notification_received|cleared`, or a templated event type; blueprints after substitution) is therefore typed (`CONFIRMATION_WATCH`). Listeners on the tap itself stay ordinary: they see the action ids only once they are dead, but their traces keep the event, and an Android tap's event carries the phone's webhook id, which never dies; trace output therefore hides it (below). Existing automations made before this change are not re-checked.
- **Late delivery:** a send still in flight when the wait ends may reach a phone after the clear; its buttons are dead (the ids lived only in that wait).
- **The linked user's own context:** a script the model wrote and the linked user then runs from a dashboard fires with that user; with a leaked id it could confirm. Narrow; stated.
- **Listening gap:** an unrelated notification action ends both listening windows at once; a tap in the milliseconds before they re-subscribe is lost (no answer, nothing sent).
- **Delivery:** push quota and push-relay errors are silent in Home Assistant (the call still succeeds): the wait then ends as no answer. A phone with no route to HA (no cloud, remote URL, or LAN) loses the tap. A swipe-away is no answer (Android's cleared event is not read).
- **Who:** one linked phone per computer and home; a household member who uses HA NOVA on their own computer links their own phone there. A non-administrator can't link or confirm.
- **Lost phone:** while it is still registered in Home Assistant, changing or unlinking asks that phone. Way out: remove it in Home Assistant (Settings → Devices & services → Mobile App), then link the new phone (§7.9); unlinking a removed phone needs the window, else editing `config.json`.
- **Linking a phone that isn't yours:** the link question goes only to the chosen phone, but a model that runs `ha-nova setup confirm-phone "<name>"` can pick another administrator's phone; where no window can open (first link, or a removed linked phone) only that person's tap stands between; the question names this computer and says to tap only while setting this up. Removing the linked phone's integration entry is a raw write #718 still allows (skills preview it); it only makes plans refuse, and relinking then needs a new administrator tap.
- **Model-edited persons:** `person/update` is a raw write, so a model can change which phones the list shows under whom (a child's phone under a parent's name); the one link question then reaches that phone, but its tap comes from a different user than the one it was listed under and is rejected, so this misleads the list but never links a wrong user.
- **No window, first link:** on a headless computer the first link is trust on first use: the tap alone links (a forged one needs another administrator's Home Assistant login or a leaked webhook id, T3). Replacing a once-linked phone never is.
- **Headless and lost:** a headless computer whose linked phone was removed can't relink by itself (no window): the user runs it at a desktop or edits `config.json`.
- **Lock screen:** the plan's summary (names, the action) shows in the notification preview.
- **MCP:** the server answers no `ping` during the up to 40 s wait, as with the window.
- **Untested:** the real Companion apps (simulated registrations only; the push payload is per the apps' sources), App mode itself (a separate admin HA user stood in for the Supervisor user), and remote connectors.
- **Language:** the notification text is English, like the window.

### 7.9 Linking (`ha-nova setup confirm-phone`, and the setup wizard)

No broadcast: a partner or child never gets a link push they don't understand and might tap.

1. **Candidates.** In the setup wizard right after "Sign in with Home Assistant" (#702): the phones on the signed-in user's `person`. Otherwise (a six-digit code, the plain command, or that user has none): every administrator's phones, as a list only. Phones of the Relay's user, of non-administrators, and with a shared notify name are never listed.
2. **Choose.** One proposed phone: "Use “Markus’s iPhone” (Markus) for HA NOVA confirmations?" (Enter, `other` for the list, `skip`). Several: a short numbered list, phone name and person, under "only administrators' phones are listed; the phone you pick gets one notification, so pick your own; yours missing: ask the owner to make you an administrator". None: how to install or sign in to the Companion app (or, when names clash, which name to fix); the next channel applies. `ha-nova setup confirm-phone list`, or the command without a terminal (an agent runs it), only lists and sends nothing; the agent then tells the user to watch their phone and runs `ha-nova setup confirm-phone "<phone name>"`. Without a terminal both asks (old phone or window, then the new phone) share one 90 s budget, under the common 120 s command limit.
3. **Allow the change.** A phone linked and usable: that phone confirms the change first. A linked phone that can never answer again (removed from Home Assistant, its user no longer an administrator, or now the Relay's user; a model can cause each): only the confirmation window approves; no window, or one that can't open, refuses (the way out is the desktop, or removing the entry from `config.json`). No phone linked yet (or the #719 pin): the window asks where one can open; where none can, the tap alone links (trust on first use). A linked phone that is unreachable or shares its name: refused with the fix (sign in again, remove or rename the other device). The link is saved only while this home's entry is still the one that was approved (a concurrent change is never overwritten).
4. **Link.** ONE notification, to the chosen phone only: "Use this for HA NOVA confirmations?" / "Requested by “<computer>”." and the platform's hint (above) with [Allow] (needs the unlocked phone, as Move and Stop do) and Cancel. Changing or stopping asks the phone linked now: "Move HA NOVA confirmations to “<phone>”?" [Move] / "Stop getting HA NOVA confirmations?" [Stop], whose body says that HA NOVA may then ask in chat, where the AI assistant can answer. The tap completes the link: it proves the phone is in hand and gives the Home Assistant user it arrives as, which must be the person's user the phone was listed under, an administrator, and not the Relay's. A decline, timeout, or any other user links nothing.
5. **Say it plainly:** "Linked “Markus’s iPhone”. Only “Markus’s iPhone” gets HA NOVA confirmations from “<computer>”."

`ha-nova setup confirm-phone off` unlinks: confirmed on the linked phone; a linked phone that can never answer again needs the window; otherwise refused. The setup wizard offers steps 1-5 after a pairing in that run, never in service mode or without a terminal; where a window opens it says so before the window appears.

**Can a model link its own phone?** It needs a tap from an administrator's Companion registration other than the Relay's user. A simulated device is a `mobile_app` registration, which needs a Home Assistant user's access token: made with the Relay's token, its taps carry the Relay's user (refused); made with a non-administrator's token, refused; made with another administrator's token, that token unlocks doors directly (T3). Raw `POST /api/mobile_app/registrations` is not on #718's REST allowlist anyway. Event forgery stays closed as in §7.6.

**Webhook ids (closed in this change, found in review):** a `mobile_app` entity's registry `unique_id` starts with its phone's webhook id, and that id alone acts as the phone without a login (`fire_event` a tap as its user, `update_registration` to redirect its pushes, even `call_service`). #718's raw allowlist served it through `config/entity_registry/list|get|get_entries` and the `update` reply. An Android tap's `mobile_app_notification_action` event also carries `data.webhook_id`, and an automation trace on that event keeps it (`changed_variables.trigger.event`; verified on the throwaway HA). Every response the CLI reads now goes through one filter (`cli/relay_raw_redact.go`): the raw route (before `--jq`), every verb read (`relay_session.go`), writes (`relay_write.go`), and `ha-nova trace` hide `unique_id`/`previous_unique_id` of `mobile_app` registry entries and `data.webhook_id` of the Companion app's notification events. The raw route and the trace verb also hide any `HANOVA_` confirmation id. An automation's own webhook trigger keeps its id. Swept on the throwaway HA with no hit: `GET /api/logbook`, `/api/history/period`, `/api/events`, `/api/states`, `/api/error_log`, WS `get_states`, `system_log/list`, `config_entries/get`, `config/device_registry/list`, `search/related`; `GET /api/diagnostics/config_entry/<mobile_app entry>` answers 404 on 2026.10.
