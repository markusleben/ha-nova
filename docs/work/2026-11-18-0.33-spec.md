## 1. MAR-209

### 1.1 Why the light asks

`ha-nova plan call light.turn_on` on one light is typed in the maintainer's home with `CALL_SERVICE_LISTENER_UNEXPLAINED`, `RUN_EVENT_LISTENER_UNEXPLAINED`, `OWNED_MEMBER`, `UNRESOLVED_TARGET` ×3, and the note `TEMPLATES_NOT_CHECKABLE`. Read from the engine and the home's read-only configs (18 November), the chain the code supports is:

1. An automation listens on `call_service` with `event_data: {domain: cover}` (`automation.rolladen_watchdog_dynamische_cover_gruppen`). Its script `script.rolladen_watchdog_check_group` waits 1 minute, posts a `persistent_notification.create` and a `logbook.log` in a dry-run branch, otherwise calls `cover.open_cover`, `cover.close_cover`, or `cover.set_cover_position` on templated targets, then waits 3 seconds. (The 0.32 spec described it without the domain filter; the current config has one.)
2. Home Assistant counts more `call_service` listeners than automations explain. An unfiltered logbook stream (a logbook panel or card) listens on `call_service` and `logbook_entry`; an entity-filtered one (an entity's history) adds `automation_triggered` and `script_started` (Home Assistant 2026.11, `logbook/helpers.py`). The engine rates such a surplus preview: `CALL_SERVICE_LISTENER_UNEXPLAINED` (`cli/tier_listeners.go:77–88`, `frontendListenedEvents` in `cli/tier_rules.go:165–169`), on every call while it lasts.
3. The same branch marks the census incomplete (`e.complete = false`). In the service-call fixed point an incomplete census makes **every** `call_service` automation a consumer, whatever its filter (`!e.complete || e.calls.mayFire(hit.filter)`, `cli/tier_callset.go:185`). So the cover watchdog becomes a consumer of a light call.
4. Inside the watchdog's run the targetless notification and logbook steps make the call set unknown (`cli/tier_walk.go:172`), the delays make the run late (`cli/tier_walk.go:30`), so its templated cover targets can't be bounded (`cli/tier_bound.go:39–45`); the home also has an access cover the template could pick. Result: typed.

This is the chain the code and configs support, not yet proof that the surplus is the only cause in that home: an unknown light platform, a loaded reactor or thermostat helper, or another completeness gap would also let the watchdog in (`cli/tier_callset.go:69–92,146–166`). The test bed proves the counterfactual on a fixture with controlled listener counts (§1.4), and the maintainer's own read-only `ha-nova plan call light.turn_on <light> --json` on the 0.33 RC confirms it for his home (the reason's detail `call_service: N live, M enumerated`, and `consumers` without the watchdog after the change). Agents never run it on his home.

The bed's M row passed in 0.32 because its copy of the watchdog has no domain filter, no delay, and no notification step, and the bed never holds a logbook stream (`scripts/e2e/testbed/mrow.mjs`). That is why the lane missed it.

### 1.2 Decision A (maintainer): an unexplained listener on a logbook-listened event

Today (maintainer default, 2026-10-14): an unexplained surplus on `call_service`, `automation_triggered`, or `script_started` is preview, and on `call_service` it also makes every service-call automation count.

Proposed: such a surplus is treated as a listener that doesn't act. It becomes a coverage note (`UNEXPLAINED_LISTENER`), not a preview, and it no longer marks the census incomplete, so each enumerated automation's literal `event_data` filter decides as it does without the surplus. Everything else that leaves the census incomplete (a read failure, an unread automation, a cut, an unknown call set) keeps today's fallback, and an unexplained surplus on any other event stays a typed gap (`UNENUMERABLE_LISTENER`), as today.

What it gives up, stated plainly: HA NOVA can't name the extra listener. If it is not a logbook view but a program that reacts to service calls by calling others (a custom integration, an external script on the WebSocket API), HA NOVA doesn't see what it calls. Today's fallback only partly covers that case anyway (it counts known automations, never the unknown listener's own effects), and HA NOVA already treats the same kind of listener this way elsewhere: an external consumer manager is a note (`NO_LOCAL_CONSUMER_MANAGER`), and custom integrations are outside the model (`docs/reference/safety.md`). A local consumer manager (Node-RED, AppDaemon) stays preview through its own reason (`CONSUMER_MANAGER_PRESENT`). `safety.md` states the change in its listener row.

Effect beyond the maintainer's home: every home where a logbook panel, a logbook card, or an entity's history is open somewhere (a wall tablet, the app) gets a preview on every service call today; with A, those calls are rated by what they do.

Options:

- **(recommended) A:** the light is 0 asks in the maintainer's home, with or without a logbook open, provided §1.1's check confirms the cause.
- **Not A:** the light stays at one window click while a logbook is open, 0 otherwise (0.32's behavior).

### 1.3 D7, the owner's "harmless" per automation version: deferred

Markus picked D7 on 2026-11-18 to stop the light asking. Reading the engine shows it can't do that, and that a sound D7 wouldn't clear the watchdog either:

- **It doesn't reach the light's preview.** `CALL_SERVICE_LISTENER_UNEXPLAINED` belongs to the unnamed listener, not to the watchdog, so a mark on the watchdog takes the light from one window click to one chat "yes", not to 0. Only decision A removes it.
- **The watchdog's cover calls run after a delay.** A templated target is rated by the entities that exist when HA NOVA checks; one that runs later can pick an entity added in between, which is why 0.32 keeps every late bound typed (the D6 review's P1). A mark that clears the watchdog would have to accept actions HA NOVA never visited, not just "any cover may move" (a cover added later can run its own script).
- **What it needs is larger than its benefit in 0.33:** a revision Home Assistant doesn't provide (a content hash comes back after an edit is reverted, and the engine's normalized digest hides some edits, `cli/tier_engine.go:424–565`), per-occurrence provenance in the engine so a waived template candidate never hides the same entity reached literally (`cli/tier_engine.go:133–152,252–285`), an owner action bound to one immutable offer, a store and two page sections on the Relay (about 130 lines against a ceiling with 2 left), and handling for computers whose CLI rates differently from the App (a CLI before 0.33 refuses with `GATE_DISAGREES` when the App needs no ask, `cli/gate_client.go:248–250`).

With A, what D7 would still change in that home is cover calls through HA NOVA (each starts the watchdog): they stay at one window click, as in 0.32. If that is worth the cost later, a D7 build must meet these contracts, all fail-closed:

- **Waives** only findings of the marked automation's own run and of the scripts and blueprints it runs by literal name: their preview reasons, and a templated target in a domain the mark names, never in `lock`, `alarm_control_panel`, or `homeassistant`, and never one that runs after a delay, wait, or reload.
- **Never waives** a typed reason of a literal target or service, a templated service name, any read failure or cut, anything reached outside the run (the plan's own target, another automation, a script by templated name), or the same entity reached by any other path.
- **Bound** to a revision of the automation and every literal dependency, read once and agreeing across the reads that use it; anything unverifiable means no mark. Any change ends the mark for good; a revert doesn't revive it.
- **Stored** on the App, written only by the owner's page action for one exact, immutable offer from the App's own check; devices, chat tools, and administrators have no write path.
- **Older pieces:** an App or CLI without the contract rates as today, and a CLI and App that disagree never send without the stricter one's ask.
- **Relay:** a reviewed ceiling raise.

## 2. `setup --server <name>` on the setup page (MAR-241)

Today the setup page runs only for the default profile with no flags (`pageFitsWithoutLink`, `cli/setup_link_leftover.go:34–38`), so `ha-nova setup --server markus-home` runs the terminal wizard and asks "Which AI app do you use?" again although the apps are set up.

Scope: an **existing** named profile. An unknown name keeps failing loud (`cli/command_setup.go:192–205`), so a mistyped name never starts setup for a new home; adding a server stays the completed-setup screen's "Add another Home Assistant server" (`cli/setup_add_server.go`).

Change:

- `pageFitsWithoutLink` no longer requires the default profile. A run that selects an existing profile by `--server <name>` or `HA_NOVA_SERVER` uses the page when the same run on the default profile would. Every other condition stays: other flags, a service install, a custom Relay address, a desktop to show the page on. The page's verbs already pass `--server` (`cli/setup_page_exec.go:40`).
- The re-pair branches (`runLinkRePair` for `pair_again` and a Link re-pair, `cli/command_setup.go:269–281`) and the named start guards (`cli/setup_flow_start.go:20–44`, `cli/setup_named_profile_guard.go`) decide the page by the same rule for named and default profiles, and keep their own checks: an interrupted retirement (`namedSetupIsRetirementOnly`), the leftover-Link choice, and the Link recovery keep the terminal where they do today.
- The page's header names the server ("Setting up “markus-home” · 10.85.1.2"), so a person with two Home Assistants sees which one.
- **The AI apps aren't asked again.** They belong to this computer, not to the profile, so a named profile reuses the saved selection, including a choice that set up no app; the question appears only when this computer has no saved selection. `keepClientsSetUpBefore` (`cli/setup_page_rerun.go:167–176`) only intersects installed apps, so the saved selection itself is what's reused.
- **Still asked:** the one-click question ("Confirm risky changes here with one click?") on every pairing, as decided for 0.32 (D2). On the page it is the preset switch under the sign-in button, not an extra step.
- Text-only runs (SSH, no display, `--no-browser`) keep the terminal, with the same rule for the AI apps.

Tests (Linux container lane only, since they pair): page selection by flag and by environment for an existing named profile; an unknown name still fails; each re-pair branch for a named profile; a retirement-only named profile in the terminal; the app question skipped on a re-pair in both UIs, also with a saved "no app" selection.

## 3. The 0.32 follow-ups (MAR-242)

One PR; each item with its regression test.

1. **The cleanup copy of the old Link sign-in goes once its revocation is proven and recorded.** After `invalid_grant` confirms that the copied refresh token is revoked and the App has acknowledged `legacy_cleanup_complete`, setup deletes exactly that item (`ha-nova.oauth.home-assistant-cloud.legacy-cleanup.<state>`) with the existing compare-and-delete, without a prompt (`cli/legacy_link_copies.go:93–115`). Before that acknowledgement the copy stays, because a retry resumes from it (`cli/legacy_link_cleanup.go:106–139`). A failed delete leaves a small receipt (the item's name and that its token was revoked, no secret) in the profile's state; while a receipt exists, setup retries the delete and doctor names it in one line, independent of the window's eligibility. The setup path deletes nothing today; uninstall and server removal already use the exact-delete helper. Tests in the Linux container lane, with a fake store.
2. **The browser setup re-run shows the cleanup's result right away.** The re-run already runs the cleanup and collects its note (`cli/setup_page_rerun.go:44–55`, `cli/setup_flow_finish.go:150–162`), but the note appears only at the end, and the `pageQuit` branch drops `pageNotes` (`cli/setup_page_rerun.go:374–386`). Show it on the re-run screen when it's known, and keep it on quit.
3. **Two failures keep their cause.** `gateMe` discards the transport, status, and decode error of `/gate/v1/me` (`cli/gate_me.go:51–75`); the Link-only setup path discards a config reload error (`cli/setup_cloud_resume.go:254–262`). Both keep a safe diagnostic cause and show it; what falls back where doesn't change.
4. **An `ok: true` envelope on an HTTP error is an error** (`cli/gate_client_call.go:81–98`): only a 2xx with `ok: true` is success. Anything else returns the envelope's code, or a status-based one when the envelope has none.
5. **`cloud remove` doesn't say "removed" during a re-pair.** Its install-identity recovery branch prints "Home Assistant Link access was removed." before it checks `rePairLifecycle` (`cli/command_cloud_remove.go:373–390`). Only that sentence is suppressed under a re-pair; the branch still prints its next recovery command.
6. **`readLegacyLinkSecret`'s doc comment** moves back above it; today it sits above `legacyCleanupPromptContextAvailable` (`cli/legacy_link_cleanup.go:144–151`).
7. **`"confirm": "code"` while `say` names the window.** `plan.confirm` names the tier (`none`, `natural`, `code` = a person's confirmation, `cli/plan_store.go:167`), and every skill reads `code` as "follow `say`/`next_step`" (for example `skills/ha-nova/SKILL.md:71`). Renaming the value would break a shipped contract (skills, MCP tool text, `TestMCPToolTextStable`), so it stays. `docs/reference/client-integration.md` says what the field means and that `plan.channel` says where the person confirms. Its sentence "A plan that needs a four-digit code (locks, gates, …) runs only with its exact code" becomes: such a plan is confirmed where `channel` says (the window, the phone, the NOVA page, a form, or the chat); a form can require a code the agent never sees (`cli/mcp_confirm.go:62–70,94–120`), and the agent never supplies one.

## Known limits

- With A, a program that reacts to service calls and that HA NOVA can't name isn't followed (§1.2).
- Cover calls in the maintainer's home stay one click while the watchdog's cover calls run after a delay (§1.3).
- **The light in the maintainer's home still asks once (rc1, 2026-11-19).** That home has a YAML generic thermostat whose heater is a YAML template switch around a plug. HA NOVA can't read either through the API, so the thermostat's calls stay unbounded (MAR-131's rule, unchanged) and every service-call automation, the cover watchdog included, counts for every call. With A, the logbook no longer adds anything; the thermostat alone keeps the light at one window click. Maintainer decision, 2026-11-19: ship 0.33 with this limit stated, and read YAML thermostats and template switches in 0.34 (MAR-245). The Go row "a YAML thermostat keeps every listener" in §1.4's tests reproduces the shape; the bed can't, because a YAML thermostat added at run time needs a Home Assistant restart and would leave every other bed row's calls unbounded.
- MAR-241 covers existing named profiles; adding one stays on the completed-setup screen.
