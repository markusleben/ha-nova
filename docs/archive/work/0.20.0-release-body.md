# 0.20.0 Release Body (final for the v0.20.0 release-prep PR)

> Bullet order expresses importance — only the first bullets feed the compact
> update notice (docs/releasing.md → Release Notes Style).

## New Features

- **Connect more than one Home Assistant.** Named server profiles in one install: add a second instance with `ha-nova pair --server <name> --relay-url <url>`, select one with `--server` on relay calls or `HA_NOVA_SERVER=<name>`, and manage profiles with the new `ha-nova server list|default|rename|remove`. Existing installs migrate automatically — nothing re-pairs, and each server's device credential stays isolated. (#343, #409, #410)
- **Update notices tell you why.** When a new HA NOVA version is available, the notice now includes the top release highlights (action-needed first) and a link to the release notes — across `check-update`, relay nudges, and session start — instead of just two version numbers. (#403)
- **One confirmation for one logical change.** A multi-step change (up to 10 non-destructive operations, e.g. a scene plus the script that activates it) shows every preview first and asks for exactly one confirmation at the end — no more menu after every step. Deletes keep their own confirmation codes, and every step still verifies individually. (#391)
- **Your earlier decisions stay binding.** In long multi-step tasks the AI now tracks what you required, chose, and rejected — a later plan that would contradict an earlier requirement is blocked and explained instead of silently applied, and only your own newer choice can replace an older one. (#395)
- **Button remaps check reality first.** Before remapping a button, remote, or wall switch, the AI verifies which gestures the device actually supports (integration metadata + real observations) and refuses to plan around a gesture it cannot confirm — offering the supported alternatives instead. (#396)
- **Repurposing an input finds its current consumers first.** Automations, scripts, event listeners, and blueprint-backed automations that still use the input are found before anything is reassigned — and if a source cannot be checked (Node-RED, AppDaemon, ...), that gap is named instead of claiming the input is unused. (#397)
- **Service setups pair like everyone else.** `ha-nova setup --service <client>` now goes straight to one-code device pairing and keeps the device credential in a protected file — no desktop keyring, no token copy-paste. (#388)
- **Headless opt-in for pairing.** `ha-nova pair --credential-store=file` stores the device credential in a private file on machines whose desktop keyring is never unlocked (agent VMs, autologin boxes, systemd user services). The locked-keyring error now names both ways out. (#388)

## What To Watch

- **Config migrates to server profiles automatically.** The first save after updating rewrites `config.json` to the new multi-server shape; your current setup becomes the `default` profile and keeps working unchanged (the old flat fields stay mirrored, so the default server keeps working even one release back). Nothing re-pairs.
- **`ha-nova setup` now always manages the default server.** Additional servers are added with `ha-nova pair --server <name> --relay-url <url>` and administered with `ha-nova server ...` — setup will tell you so if a different profile is selected.
- **Service re-setups switch storage.** An existing `--service` install that kept its device credential in the desktop keyring moves it to the protected file on its next `setup --service` pairing — the documented service behavior. The old keyring entry becomes inert; nothing breaks mid-upgrade.
- **Older Relay Apps get a clear nudge.** The supported minimum Relay version is 0.7.0; CLI health checks and doctor steer straight to the App update instead of surfacing bare auth errors against pre-pairing relays. The Relay App itself is unchanged in this release — no App update needed if you are already on 0.7.0.
