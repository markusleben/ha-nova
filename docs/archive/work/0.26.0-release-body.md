# v0.26.0 — release body (archived)

Shipped wording lives in `.goreleaser.yml`; this file archives the drafted
body for the record. v0.26.0-rc1 shipped with Relay App 0.9.1; v0.26.0-rc2
and the final release ship Relay App 0.10.0 (`min_relay_version` 0.10.0,
required while Cloud is enabled). The rc2 and rc3 drafts are appended at the end.

## New Features

- Reviews and writes load less mandatory context: the stale vendored
  templating snapshot is retired in favour of the live render loop and the
  official templating page on demand; output rules are read once per
  session.
- New read-only commands `ha-nova find`, `ha-nova get`, and `ha-nova history`
  look up entities (case- and accent-insensitive, aliases included), read a
  state or stored automation/script/scene config, and summarize recent
  history in one call each. They can never change anything in Home
  Assistant, and they report available updates alongside the answer.
- New commands `ha-nova call` and `ha-nova apply` control devices with the
  safety checks built in: unambiguous everyday actions run immediately and
  are verified afterwards; everything else shows a preview first; unlocking a
  door, opening a gate or garage door, and disarming the alarm need a
  confirmation code. A call is sent exactly once and never retried, and a
  confirmed plan is re-checked first — if anything changed since the
  preview, nothing is sent and a fresh preview comes back.
- Automations and scripts can be created, updated, deleted, and reverted
  through `ha-nova plan write|delete|revert` and `ha-nova apply`: every
  change shows its diff first, is saved exactly once, reloaded, and read back
  to verify it; deletes need a confirmation code and take a config snapshot
  first, and the last update stays one step revertible. (#664, #666)
- **Prebuilt Relay App images.** Installs and updates download a ready
  image (`ghcr.io/markusleben/{arch}-ha-nova-relay`) instead of building on
  the Home Assistant device: faster, and no more failed builds on low-RAM
  devices. (#674)
- `ha-nova find` also lists by `--domain`/`--area`/`--state` without a
  phrase ("which lights are on?"), and `ha-nova history --until` reads a
  bounded window. (#668)

## What To Watch

- **Update the NOVA Relay App too.** The release needs Relay 0.9.1 (Relay
  fixes below); Container/Core installs pull the new image. Until then the
  CLI warns that the Relay is outdated.
- **Some YAML-only controls now need a code.** HA NOVA cannot see what a
  YAML-defined button or switch without a `unique_id` does (a template
  switch could unlock a door), so controlling it is typed
  (`UNREGISTERED_ACTUATOR`). Adding a `unique_id` fixes it for
  MQTT/KNX-style switches; template and command_line entities stay typed,
  and so do MQTT/ESPHome buttons (`USER_AUTHORED_BUTTON`). YAML groups stay
  preview with their members classified.
- **The safety promise has one explicit exception now.** Unambiguous
  everyday actions run immediately and are verified afterwards; everything
  else shows a preview first; locks, gates, alarm, and deletes need a code.
  The HA NOVA command decides which is which, never the AI — and it sends
  nothing when anything changed since a preview.
- **Automation and script deletes use one code per item.** The
  confirmation code for deleting an automation or script now comes from
  HA NOVA for that exact delete; a multi-item delete asks for each item's
  own code instead of one code for the whole list. Reverting an update that
  was changed in the Home Assistant UI since is refused instead of
  overwriting that edit.
- **Malformed Home Assistant replies now fail loud.** A core REST reply
  whose body is not valid JSON or not valid UTF-8 is reported as an upstream
  error (`502 / UPSTREAM_HTTP_ERROR`) instead of a successful empty result.
- **`RELAY_PORT` must be a plain integer.** Values such as `8791oops` or
  `1.5` are rejected at startup instead of silently starting on a different
  port.
- **Private App files must belong to the App and be owner-only.** A
  restored `/data` whose files are readable by other users is repaired to
  owner-only on first read; files owned by another user stop the App with a
  message naming the `chown` fix — never with a registry reset offer.
- **Shared legacy access is being retired.** App installs that still use
  the old shared access from before per-device pairing keep working in this
  release and the next one; the release after that no longer accepts it.
  Re-pair each computer
  once with `ha-nova pair` (one six-digit code each), then revoke the old
  shared access on the NOVA page. The standalone container's shared token
  is retired on the same schedule and moves to the same one-time-code
  pairing over a pinned connection.
- **Leaner: the optional Census is removed.** It was always opt-in and off
  by default; dropping it keeps HA NOVA small and simple. The CLI removes its
  old local Census setting on the first run, and `ha-nova census …` no
  longer exists.

## Bug Fixes

- YAML and package automations/scripts are read through their loaded
  config, so one id-less YAML automation no longer forces confirmation codes
  on unrelated actions; such items are marked `managed: yaml` and routed to
  YAML editing instead of plan write. (#668)
- Verification notes are honest: a device that has not reached the target
  state is reported as "still locked after 10s", and a late failed read
  keeps the last good observation. (#668)
- A Home Assistant that rejects the Relay's token no longer causes an
  endless reconnect loop (one HA auth notification per attempt). (#651)
- The setup intro describes the one-time six-digit pairing code instead of
  access tokens. (#652)

- Home Assistant 2026.9 child devices (`parent_device_id`, reduced rows,
  inherited area) are modeled once in the shared membership-resolution
  contract and used by health, capability answers, and fallback resolution.
- Update install/skip/clear-skipped are administrator-only since HA 2026.9:
  a standalone Relay with a non-administrator token gets a clear diagnosis
  instead of an opaque failure.

- A Home Assistant WebSocket peer that accepts the connection and never
  finishes authentication no longer wedges every later Relay call: the
  handshake has a deadline, and an abandoned connection is closed instead of
  reconnecting next to its replacement.
- Pairing, management-page actions, and owner verification log the real
  cause of a persistence or lookup failure for the operator; the replies a
  client sees stay unchanged.
- A malformed owner lookup answers "verification unavailable, retry"
  instead of a false "owner access required".
- Windows: the updater no longer leaves `ha-nova-updater-*.exe` in `%TEMP%`,
  a failed updater launch cleans up its staged download, and the uninstall
  helper removes itself on every exit.
- Configuration snapshots: concurrent saves can no longer exceed the store's
  hard file and size caps; a snapshot removed while the store is being
  scanned no longer fails the scan.
- The management page and health endpoint keep answering when the snapshot
  store is unreadable, and the operator log says why.
- Headless Linux: `ha-nova uninstall --purge` works on installs without an
  unlocked keyring (service mode, file-stored credentials) instead of
  stopping at "secure storage unavailable" and removing nothing.
- Codex CLI and OpenCode can use `ha-nova setup --service <client>` on
  headless machines and SSH sessions; and re-running `ha-nova setup` there
  keeps an existing service token file instead of demanding the keyring.
- fish users: the installer puts `~/.local/bin` on PATH through
  `~/.config/fish/conf.d/ha-nova.fish` (other unknown shells: `~/.profile`),
  and uninstall removes the PATH entry from every file the installer could
  have written.
- Uninstall wording: the summary names the relay token file when one is
  used, and the server-side checklist covers standalone relay containers.

## Internal

- Every GitHub Actions step is pinned to an immutable commit SHA, and CodeQL
  scans the Go CLI fail-closed.
- The per-pull-request release gating is replaced by release-time checks:
  signed Cloud bundle provenance, three-OS install smokes, and a per-release
  Cloud checklist.
- Route-level context ratchets for the review and write skills (#521).
- A seeded throwaway Docker Home Assistant test bed for contributors
  (`npm run testbed:*`), run weekly against the latest Home Assistant stable
  with an automatic pin-bump PR. (#667, #669)
- Setup tests no longer reach a developer's local HA/Relay default ports.
  (#662)

## Release-prep README edits (applied in the release-prep PR)

- Skills first: reframe "Why not an MCP server?" as "Why skills first, not a
  tool server?" — one readable skill on demand instead of a tool catalog. The
  `ha-nova mcp` adapter ships in the binary but stays experimental and
  unadvertised (hidden from `ha-nova --help`, no README or release-note
  claim) until it carries the skills.
- Confirmation-code honesty: wherever the README promises codes ("You
  approve it", typed codes for locks/gates/alarm/deletes), add that a code
  only proves it was you when your client asks before the apply step runs —
  the AI sees the code it relays; HA NOVA tells it never to use one you did
  not type.
- Batch deletes: README step 3 "A reviewed batch delete takes one code bound
  to the exact list of items" no longer holds for automations and scripts —
  each delete is its own plan with its own code.
- Typed verbs: the README promise "Every change is previewed and approved
  first" (tagline) and "device control get preview-and-verify" (feature
  note) change to the fast-path wording above — unambiguous everyday actions
  run immediately and are verified afterwards; everything else shows a
  preview first; locks, gates, alarm, and deletes need a code.
- Census removal: delete the README "Census off by default" Safe-by-Design
  bullet (it also links the removed `docs/reference/census.md`), and change
  the `ha-nova uninstall --purge` row to say it retains small opaque local
  markers that block stale processes from restoring the install.
- Headless Linux (README "Linux — proven end-to-end, including headless
  setups"): add that a standalone relay (relay token, no device pairing) on a
  machine without a desktop keyring uses `ha-nova setup --service <client>`
  (Codex CLI, OpenCode, Hermes Agent).

## rc2 additions (consumed `docs/work/next-release-body.md`, #673–#722)

### New Features

- A room or device command that reaches exactly one matching device ("turn
  off the kitchen lights" with one light there) now runs right away and is
  verified, exactly like naming that device. Rooms with several matching
  devices and groups still show a preview first.
- **Faster setup on extra computers:** when the NOVA Relay App already runs on
  your Home Assistant, setup skips the install steps and goes straight to
  pairing this computer.
- **Sign in with Home Assistant to pair:** setup opens your Home Assistant
  login in the browser. Sign in as the owner, and setup connects this computer
  by itself, with its own connection that you can remove in NOVA at any time.
  Over SSH, with an older NOVA Relay App, or when sign-in does not work out
  (for example another Home Assistant user), setup uses the one-time six-digit
  code from NOVA as before.
- **One install link:** setup opens the NOVA Relay App page directly and adds
  the repository on the way — click "Add", then Install and Start.
- **A first look right after pairing:** setup ends with your home in one
  line, up to two things worth a look (a low battery, an automation that
  can't run), and example prompts that use your own room and device names.
- **Know your home with exact numbers:** ask "what do I have?", "where is
  this sensor used?", or "review my whole setup" — rooms, devices,
  automations, integrations, unavailable entities, and low batteries are
  counted by HA NOVA itself, so the AI never guesses a number or a name.
- **Undo a deleted automation or script:** "undo that" right after a delete
  restores it from the copy saved before the delete, under its original
  id, with the usual preview. It never replaces an item that exists.

- **Replace a device or a phone:** "my door sensor died, I paired a new
  one" or "I have a new phone" moves automations, scripts, scenes,
  dashboards, helpers, energy sources, notifications, and presence to the new
  device in one reviewed plan. When the old device is gone for good, the new
  one takes over its entity ids, so history and statistics continue.
- **Build whole dashboards:** ask for a dashboard or a view and HA NOVA
  builds it, reorders or removes views, and uses custom cards you have
  installed. The preview lists every view and card that changes; a copy is
  saved before each save, and "undo that" restores the previous version.
  "Check my dashboards" lists cards that point at missing entities or at
  custom cards that are not installed.
- **Move your rules to Home Assistant:** paste a Node-RED, Homey,
  SmartThings, Hubitat, or openHAB rule, or point at old automation YAML, and
  HA NOVA turns it into a native automation. It first lists what the rule
  does, maps each device to a real Home Assistant entity (or asks), and names
  anything it cannot translate. The old rule stays disabled, not deleted,
  until the new one has been checked against that list.
- **ESPHome device configs:** ask what a device in `/config/esphome/` does,
  or to check it, and HA NOVA explains it in plain words and flags keys that
  newer ESPHome releases removed, pins that cannot do what the file asks, and
  passwords written into the file. With file access turned on, edits show the
  changed part first and save a copy. Passwords and keys are never shown. Installing on the device stays
  in the ESPHome App; afterwards HA NOVA checks that the device's entities
  came back.

### What To Watch

- **Home Assistant Link:** Nabu Casa is renaming Home Assistant Cloud to
  Home Assistant Link (same subscription, same features). HA NOVA's setup
  and messages now say Home Assistant Link. Commands stay the same
  (`ha-nova cloud …`), and until the rename reaches your Home Assistant, the
  setting is still under Settings > Home Assistant Cloud.
- **Shorter one-time codes:** unlocking a door, opening a gate or garage,
  disarming the alarm, and deletes now ask for a four-digit one-time code from
  HA NOVA ("Type 4821 to unlock “Front Door”") instead of a long
  `confirm:…` code. A plain "yes" still can't confirm, and a code works only
  for its own plan. A plan shown before the update has to be made again.
- **Confirm on your computer, not in chat:** where your computer can show
  one, these actions now open a confirmation window — click Confirm there, or
  Cancel. This also replaces the confirmation form in apps that show one; the
  form stays where no window can open. Your AI assistant never sees a code. It still can click the window
  if you allow it to control your screen (computer use, or apps you granted
  Accessibility), and on Windows and some Linux desktops other programs can
  too. To turn the window off: `ha-nova setup
  confirm-window off` (you confirm that in the window).
- **Or confirm on your phone:** over SSH, without a desktop, or where the
  window can't open, HA NOVA sends Confirm and Cancel to the one phone you
  linked (Companion app): hold or expand the notification and press Confirm
  (the phone asks for Face ID, fingerprint, or passcode). Setup offers to link
  your phone right after you sign in with Home Assistant, or run
  `ha-nova setup confirm-phone`: pick your phone, then tap "Yes, link" on it.
  Only the linked phone ever gets HA NOVA confirmations, nobody else's in your
  home, and only its Home Assistant user (an administrator) counts. Not with a
  standalone NOVA Relay that runs on the owner's own token. Without a linked
  phone, HA NOVA shows the one-time code in chat as before and says that the
  assistant can see it too.

#### What To Watch (phone confirmation)

- Once a phone is linked, an unlock or delete is refused (nothing changes)
  when HA NOVA can't reach that phone, instead of falling back to a code in
  chat. Changing or unlinking it (`ha-nova setup confirm-phone off`) is
  confirmed on that phone. Lost it? Remove it in Home Assistant (Settings →
  Devices & services → Mobile App), then link the new one.

- `ha-nova uninstall` no longer guides removal of the NOVA Relay App by
  default. It first asks whether this is the last computer using HA NOVA,
  because removing the App disconnects every paired computer.
- Pressing a button, turning on a switch, or opening a cover on a device
  that also has a lock, alarm, or access cover now needs a one-time code. Configuration
  and diagnostic buttons there (ping, identify, restart) work as before.
- HA NOVA now only makes the low-level changes it has a checked rule for.
  Settings changes through an integration's own interface (Z-Wave, Zigbee,
  Alarmo, and others) are pointed to the Home Assistant UI instead, so none
  of them can open a lock or disarm an alarm without the one-time code.

### Bug Fixes

- Room and device commands now skip hidden entities and configuration or
  diagnostic entities, as Home Assistant's own room targeting does; when that
  leaves nothing, the answer names the skipped entities. A device command
  also reaches the device's child devices, as Home Assistant does.

## rc3 additions (consumed `docs/work/next-release-body.md`, #727–#729)

### Bug Fixes

- Windows (and macOS) setup over SSH, or in an administrator terminal, now
  says what to do when secure storage can't be reached: sign in to the
  desktop of the computer HA NOVA is installed on and run `ha-nova setup` in
  a normal terminal there. The raw error stays as a detail line, a localized
  Windows error is recognized too, and `ha-nova pair` and `ha-nova doctor`
  give the same next step.
- A local-only install no longer blames Home Assistant Link when this
  computer's secure storage is unavailable; the message names this
  computer's saved credential and says how to unlock it.
- The Windows installer on an ARM PowerShell now lists the exact steps to
  get the x64 PowerShell (download the `-win-x64.zip`, extract, open
  `pwsh.exe`) instead of "use x64 emulation".
- On the first Windows setup, the wizard explains the Windows Firewall
  prompt raised by the network search for Home Assistant: Cancel is fine,
  setup continues, and you type the address if nothing is found. (Wording
  corrected at release prep; the draft said "either answer is fine".)
- The installers, the setup intro, and the first-look safety line match how
  this computer pairs and confirms: sign-in as the owner or a six-digit code
  from the NOVA page, and "confirm it yourself" for unlocks instead of always
  promising a one-time code.

### Release-prep README edits (applied in the rc3 release-prep PR)

- README says that over SSH setup "asks for the code instead". On Windows,
  pairing over SSH (key sign-in) can't save the credential either way: pair from the
  computer's own desktop (Credential Manager needs a desktop sign-in).
