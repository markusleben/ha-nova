# Safety guarantees

What HA NOVA promises, what enforces it, and what proves it. Every row names a file you can read and a test you can run — no adjectives.

Last verified: 2026-07-11 — `npm run verify`, `go test ./...`, and the live end-to-end run against a real, disposable Home Assistant (`bash scripts/e2e/disposable-ha/run.sh`), all green. Re-verify this date on the exact release commit before publishing.

The Home Assistant Link (formerly Home Assistant Cloud) rows below document the Beta's enforced contracts.
Every publication carries signed bundle provenance and passes the three-OS
release smokes; the maintainer works through the per-release Cloud checklist in
`docs/releasing.md`.

## Writes

HA UI parity batch 1 (0.29) adds raw writes the Home Assistant UI makes: integration enable/disable, rename and system options, ignoring a discovery, user account edits, general settings, ignoring a repair, exposing new entities to voice, and blueprint deletion (`cli/relay_raw_allow.go`). The raw guard refuses disabling, enabling, or changing polling of an integration entry that has a lock, alarm panel, or access cover, including one whose switch backs a `switch_as_x` access entity (removing that entry, one of its subentries, or the switch itself is refused the same way), and any access change (administrator flag, active state, local-only) to the owner's account, a system account, or the account HA NOVA uses; an unreadable registry or account list sends nothing. Access changes, time zone or unit changes, a new area or label on a device with a lock, alarm panel, or access cover (a rooms plan refuses such a device), and blueprint deletion are typed; the rest are previewed. Since 0.28.1, a URL Home Assistant stores with a password in it is refused before anything is sent, in `ha-nova relay ws` and raw plans alike, also one Go's URL parser can't read or reads without it: its own internal and external URL, a blueprint's source (also in the blueprint's YAML), and a person's or area's picture (`cli/relay_raw_urls.go`). Proof: `cli/plan_raw_tier_test.go`, `cli/relay_raw_urls_test.go`.

HA UI parity batch 3a (0.31) adds automatic backup settings (`backup/config/update`, previewed; typed with a retention, which deletes older automatic backups), Labs features (`labs/update`, typed), statistics import (`recorder/import_statistics`, typed: stored rows for the same hours are overwritten), and analytics sharing (`analytics/preferences`, previewed). The raw guard refuses any backup settings change that sets or clears the encryption password (`create_backup.password`), changes which locations encrypt (`agents.<id>.protected`), marks the first automatic setup done (`automatic_backups_configured`), carries a `create_backup` or `agents` value it cannot read, or sends a partial schedule or retention block (Home Assistant resets the rest), on every route (relay, plan, chat, collect_events envelope). Adding a remote location reads the saved settings live and is refused while no key is saved or the read fails; `backup/generate` with its own `password` or a remote location is refused, since Home Assistant uploads without a key unencrypted; the encryption key stays in the Home Assistant UI, and reads keep hiding the stored password (`backup/config/info`). Proof: `cli/plan_raw_tier_test.go`.

Device deletion sends Home Assistant's own `config/device_registry/remove` (HA 2026.9+) as a typed raw plan, the same on a computer and in chat apps, after a metadata snapshot and a preview of the entities and consumers that go (`organize`). The raw guard refuses a device that has, or whose child devices have, a lock, alarm panel, or access cover, and HA NOVA's own App device; an unreadable registry sends nothing. There is no undo. Proof: `cli/device_delete_test.go`, `cli/plan_raw_tier_test.go`, `tests/skills/routing-contract.test.ts`.

A to-do reorder (`todo/item/move`) goes only through `ha-nova plan raw` (in chat apps `ha_plan` kind raw); `ha-nova relay ws` refuses it before anything is sent, also inside a `collect_events` envelope. On the built-in shopping list a reorder fires `shopping_list_updated`, and only the plan classifies what listens to it: an automation that unlocks on it makes the reorder typed. Proof: `cli/relay_raw_endpoint_test.go`, `cli/tier_fewer_asks_test.go`.

An automation or script save sends no reload of its own: Home Assistant's config view reloads after every save (an automation by its id, scripts in full), as a save in the Home Assistant UI does, and `ha-nova apply` only checks, read-only, that Home Assistant runs the saved config (maintainer decision B, 2026-11-10). A delete still sends its reload, asked for with it. A save is rated by the config it saves, not by what Home Assistant's own reload after the save sets off (maintainer decision 2026-11-09, as in 0.28.3). Known limit: saving an automation can start automations that listen for automation reloads (`automation_reloaded`), and saving an automation or script can start automations that watch its state or match the reload's service call. HA NOVA doesn't check those before the save, just as a save in the Home Assistant UI doesn't. Nor does it check automations that listen for the service calls the saved automation or script makes when it later runs (`call_service`). If such an automation unlocks, opens, or disarms, the save doesn't ask for it. A reload you call yourself (`ha-nova call automation.reload` or `script.reload`) is still rated with what it sets off. Proof: `cli/tier_reload_test.go`.

An automation that listens for service calls (event `call_service`) counts for a plan only when one of the calls the plan sets off can match its literal `event_data` domain and service (MAR-127). The calls are the plan's own, the ones Home Assistant makes for it (a toggle, a scene's members, a group's members, a `switch_as_x` entity's switch), and the actions of every automation and script it starts. When those calls can't be bounded, every such automation counts: a templated or targetless call, a reload, a service that passes on to others (`tts`, `notify`, `conversation`, `camera.play_stream`, and the others in `cli/tier_callset.go`), an entity of an integration that isn't built in or of a built-in one that calls services itself (template, universal, and others), a consumer manager such as Node-RED, or a home where a built-in integration calls services on its own when other entities change (`alert`, `flux`, `device_sun_light_trigger`). A generic thermostat or hygrostat calls only `homeassistant.turn_on` and `turn_off` on the switch or fan its options name (MAR-131): for one set up in the UI, HA NOVA reads that entity by starting the helper's options flow and aborting it unsaved (only these two built-in integrations, and only when the home has a service-call listener), and adds those calls (on a NOVA App with the safety check, the App's own check reads it the same way); a YAML one, a read or abort that fails, a group or `switch_as_x` in between (one without a device counts for every switch without one), a script or group tied to that switch or its device, an automation whose triggers match either or the helper itself, or any automation on `state_changed` events leaves the calls unbounded. Planning from a chat app at any level can start and abort these flows; the code picks them, never the model. Known limit: the service calls that YAML trigger-based template entities make from their actions, that custom integrations make on their own, and that device firmware asks for (an ESPHome `homeassistant.action`, a phone's action) are outside this model, as they are outside every automation check (maintainer decision 2026-11-09). Proof: `cli/tier_callset_test.go`, test bed step h (`scripts/e2e/testbed/calls.mjs`).

An automation whose trigger targets an area, a floor, a label, or a parent device (the room triggers Home Assistant's editor builds since 2026.7) counts for a plan like one that names the entity (MAR-142). Home Assistant indexes such a trigger under that area, floor, label, or device, so the scan also reads the entity's area (its own, else its device's, else that device's parent's), that area's floor, its device's parent device, and the labels of the entity, its device, that parent, and the area. Home Assistant relates to an area every automation of the devices and entities in it, and to a floor those of all its areas, so each one found there is read. It counts only when a trigger targets one of these places (or targets by template), whatever it reacts to: then it may fire. The others cost no consumer read, so only the check's time limit bounds them: on a slow connection, a call in a room or on a floor with many automations can run out of time, and the plan then asks (D for 0.30: a direct-reference index). An `exclude` block doesn't take the entity out, because Home Assistant applies it only when the trigger runs. A registry the scan can't read makes the plan typed. Not checked: a trigger target written as a template, which Home Assistant can't index. Proof: `cli/tier_places_test.go`, test bed step h (`scripts/e2e/testbed/calls.mjs`).

`ha-nova relay ws|core|files|backups` refuses every write a raw plan rates typed on its own (a skill's `"typed":true` only raises a plan, so relay cannot see it), before anything is sent and also inside a `collect_events` envelope: only the user may confirm it, so it goes through `ha-nova plan raw`, then `ha-nova apply` (in chat apps `ha_plan` kind raw). The tier is the plan's own (`rawItemTier`), never a second list. Relay first tiers the request without reading Home Assistant; only where the tier depends on live state (a lock, alarm panel, or door in the target's family, the energy lists, a repeating calendar event, a person's trackers, and what a rename or an area, floor, or label change newly reaches: the registries and `search/related` for each new place) does it read, and a read that fails refuses. A person create that names trackers, and a person update that leaves a different tracker set than `person/list` shows, are typed on every route; an update without `device_trackers` empties them in Home Assistant, so it counts as a change for a person who has any. So is renaming or disabling a device tracker a person follows, or renaming one onto such an id: Home Assistant drops a tracker from a person only when it is removed. Disabling the device (or its parent device) or the integration entry such a tracker belongs to disables it too, so that is typed as well. Proof: `cli/relay_typed_test.go`.

A raw write that changes an entity's state or attributes is tiered by the automations that listen to that entity, as a call is (#946): calendar event writes, helper, person, zone, and tag updates and deletes, a new zone or person and a home-location change (`zone.home`, the sun, and every person, GPS tracker, and zone), a unit system change (every entity shown in its units), an entity registry update beyond its area, labels, aliases, categories, or visibility, a device update (with its child devices when it enables, disables, or removes), an integration enable, disable, or update, a subentry change, an entity or device removal, the start of an options, reconfigure, or subentry flow, and a scene save. An enable, an integration update, a flow, and a scene save reload their integration or every scene, so every entity they reload is scanned. One that unlocks, opens, or disarms makes the write typed, and so does a read that fails. What those automations call counts against automations that listen for service calls, as for a call (MAR-148). A write that also moves what it changes to another area or label is typed, since the check reads where it sits now (MAR-142). Two writes are rated by more than what changes state (0.31, `cli/tier_raw_takeover.go`): a registry rename onto an id (`new_entity_id`) by every automation and script that names that id, also through a group or person holding it, whatever their triggers (a takeover hands them to this entity); an entity or device moved to an area or given labels, and an area put on a floor or given labels, by every automation whose trigger targets a place it newly sits in: the new area, its floor and labels, the new labels, or the area's new floor (an entity or device whose own area is cleared sits where its device or parent device does; a place it already sat in widens nothing). A rooms plan (`ha-nova plan rooms`, its undo, the setup page's room suggestions) checks each device move the same way and refuses one that would be typed before any device moves, as it refuses a lock's device: that move goes as a raw plan, which asks. One with an action that needs confirmation makes the write typed, and a read that fails is typed. `ha-nova relay` runs the same check before it sends and refuses a typed one, naming the plan; `ha-nova plan raw` and `ha_plan` kind raw ask. Not checked: a new entity that takes an id an automation already listens to, a write's own bus event (`entity_registry_updated`, `device_registry_updated`, `core_config_updated`), later steps of an options or reconfigure flow (repair and subentry flow steps are typed), a trigger that targets the place only through a condition, what a reload runs inside the integration, entities without a registry entry, an integration that follows the home location on its next refresh (weather), a template trigger `search/related` doesn't list, and small side effects of energy, backup, Assist pipeline, HACS, and Supervisor App option writes. Spec: `docs/work/2026-11-05-raw-write-listeners-spec.md`. Proof: `cli/tier_raw_listeners_test.go`.

Known limits of the Supervisor route: log text passes as the Supervisor returns it (except its `invalid options` lines), so a credential an App writes into its own log is not hidden. The options merge sends the stored options, defaults included, so they become the App's saved settings. Chat apps give every chat user the owner allowed the same reach, under the same tiers. Home Assistant Link does not carry the route; Supervisor access works only on the local connection. The manager role widens what a Relay defect could reach: the allowlist is the only boundary between a paired device and the Supervisor's App, store, and log APIs. The table is pinned to Supervisor 2026.10.3; a later Supervisor may change its paths or role table (`docs/work/2026-10-26-supervisor-role-spec.md`).

## Honesty rules

These are guarantees about what HA NOVA *says*, which matter as much as what it does:

| Guarantee | Enforced by | Verified by |
|---|---|---|
| A successful write is never reported as verified behavior — persistence is not the same as "it works" | `skills/ha-nova/write-safety.md` → Verification Honesty ("never a bare 'verified'"); CLI result lines in `cli/say_lines.go` | `tests/skills/write-delete-safety-contract.test.ts` |
| Conclusions are bound to evidence; without it, hypotheses are labelled as such | Context skill → Claim-Evidence Binding; `skills/diagnose/SKILL.md` | `tests/skills/honesty-and-gate-pins.test.ts` |
| A notification that Home Assistant accepted is not claimed as delivered to your phone | `skills/notify/SKILL.md` | `tests/skills/honesty-and-gate-pins.test.ts` |
| An empty MQTT window means "nothing was published", and retained broker replays are never counted as live device traffic | `skills/mqtt/SKILL.md` | `tests/skills/honesty-and-gate-pins.test.ts`; `tests/skills/test-run-contract.test.ts` |
| Internal review codes (R-18, H-09, …) never reach you — findings are described in plain language | `skills/ha-nova/output-rules.md`; `skills/review/checks.md` → Output Guardrail | `tests/skills/skill-template-contract.test.ts` (check-code leak allowlist) |

## Reproduce it

```bash
npm run verify                            # typecheck + full test suite + build + documentation fact-check
(cd cli && go test ./...)                 # CLI: keyring, snapshot/revert, uninstall teardown, update nudges
bash scripts/e2e/disposable-ha/run.sh     # boots a REAL Home Assistant and verifies the relay against it
```

The last one is the honest one: it boots Home Assistant in a container, completes its onboarding, mints a token, starts the relay against it, and asserts the guarantees that only a live system can prove — authentication is enforced, the version the CLI compares against is real, proxied calls return actual Home Assistant data, a bare subscription is rejected while a bounded window is served, and the health endpoint neither opens a connection nor lies about one. It runs weekly in CI (non-blocking: it is evidence, not a merge gate) and can be run by anyone in about three minutes.

Everything is torn down afterwards; nothing touches your own Home Assistant.

The documentation fact-check (`scripts/check-docs.sh`) is deliberately hostile to its own README: it fails the build if the relay grows known domain-logic or endpoint-family patterns, adds configured analytics-vendor patterns, or gains a second implementation.
